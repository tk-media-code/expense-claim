# gmail-probe

依頼メールを Gmail API から読めるかを実機で確かめる検証スクリプト（Issue #19）。
**アプリ本体とは切り離した使い捨て**で、ここでの技術選定はアプリの技術選定ではない。

要求分析の未確定事項に「Gmail の依頼メールを読めるか」が1件だけ残っていた。
委託元の送信先が独自ドメインへ切り替わり、**案件詳細と依頼無しの2種類が実際に届いた**ので、
ここで確かめて閉じた。結果は要求分析 6章・8.6 に反映してある。

依頼メールには**ご両家名・会場名・緊急連絡先・他スタッフの氏名とメールアドレス**が入っている。
このリポジトリは public なので、**端末には実データを出さない**。伏せ方は `mail-util.cjs` の
冒頭に書いてある。

## 準備

### 1. Google Cloud

**手順と、その理由は [`docs/google-cloud-basics.md`](../../docs/google-cloud-basics.md) にまとめてある。**
`sheet-probe` と同じプロジェクト・同じ OAuth クライアント・同じトークンを使う。
`gmail.readonly` は最初からスコープに入っているので、**追加の認可は要らない**（実機で確認済み）。

### 2. このリポジトリ側

```bash
cp .env.example .env      # 実値を入れる。コミットしない
npm --prefix tools/gmail-probe install
```

`.env` に次の2つが要る。**どちらも委託元が特定できる値なのでコミットしない（N-08）。**

| キー | 中身 |
| --- | --- |
| `GMAIL_LABEL_NAME` | 依頼メールに付けている Gmail ラベル名 |
| `GMAIL_SENDER` | 依頼メールの差出人アドレス |

`venue-check` は `SPREADSHEET_ID` と `MY_SHEET_NAME` も使う（`sheet-probe` と共用）。

## 使い方

```bash
node tools/gmail-probe/probe.cjs labels       # ラベル名からラベルIDを引けるか
node tools/gmail-probe/probe.cjs list         # ラベルと差出人で同じ集合が返るか
node tools/gmail-probe/probe.cjs dump         # MIME 構造と本文を out/ へ落とす
node tools/gmail-probe/probe.cjs parse        # 件名で2種類を判別し、項目を取り出せるか
node tools/gmail-probe/probe.cjs venue-check  # 会場コードがマスタに実在するか（parse の後）
```

**すべて読み取りのみ。** `gmail.readonly` しか持っていないので、書き込み・削除・既読化は
起こり得ない。`sheet-probe` のような段階分けと都度承認は要らない。

出力の全文は `tools/gmail-probe/out/` に残る。**ご両家名・他スタッフの氏名とメールアドレス・
緊急連絡先を含むため、決してコミットしない**（`.gitignore` の `tools/**/out/` で除外済み）。

## 何を確かめているか

| コマンド | 確かめること |
| --- | --- |
| `labels` | Gmail API の疎通、ラベル名 → ラベルID、ラベルの種別（`user` なら自分で作ったもの） |
| `list` | ラベルで引いた集合と `from:` で引いた集合が一致するか、宛先で判別できるか、転送が挟まっていないか |
| `dump` | MIME 構造、`text/plain` の有無、文字コード、`text/plain` と `text/html` で何が落ちるか |
| `parse` | 件名で2種類を判別できるか（R-01 / R-19）、6.1 の項目を取り出せるか |
| `venue-check` | 依頼メールの会場コードが提出シートの会場マスタに実在するか（N-14） |

## 実装上の判断

**認可は `sheet-probe/auth.cjs` を require して使い回す。複製しない。**
`gmail.readonly` を含むスコープ定義が2箇所に増えると、「今どこまで許可しているか」が
追えなくなる。スコープは狭く保つのが原則で、その原則は定義が1箇所にないと守れない。

**本文は `text/plain` を主に読み、スタッフ割当だけ `text/html` から採る。**
実物を落として比べたところ、同じ内容を持つが落ちるものが違った。

| | 残るもの | 落ちるもの |
| --- | --- | --- |
| `text/plain` | 8本のリンクの URL | 表のセル境界。スタッフ2名が空白区切りの4語に潰れる |
| `text/html` | `td` の境界（タブとして取り出せる） | `href`（本文テキストに現れない） |

**先頭4行は位置で読むしかないが、裏を取ってから採る。**
1行目の日付が「施行日」行の日付と一致し、4行目が `〇〇様 △△様` の形であることを
確かめてから、2行目を会場名・3行目を会場コードとして採る。
**書式が変われば裏取りが失敗し、黙って別の値を拾うのではなく「取れなかった」と分かる。**

**会場マスタの在り処を決め打ちにしない。**
提出シートの B 列に付いている入力規則（`ONE_OF_RANGE`）が参照している範囲そのものを読む。
マスタのシート名や行数が変わっても追随でき、**これは N-14 でアプリがやるべき手順と同じ**。
