# 最終レビューを通して印を付ける

**PR を作る前に、ブランチ全体の最終レビューが1回要る。** 通したことを印で残し、`gh pr create` のときに
hook が印を確かめる。印が無ければ PR は作れない。

観点表は、このスキルと同じフォルダの `checklist.md` にある。読むのはレビュアーで、統括役は読まなくてよい。

## 1. 最終レビューが済んでいるかを確かめる

次の両方を満たしていれば済んでいる。3 へ進む。

- この作業のブランチ全体を対象に、`reviewer` へレビューを出した
- その報告に「観点ごとの結果」がある

**タスクごとのレビューは、最終レビューの代わりにならない。** 範囲がタスク1つ分で、観点表も読まない。

## 2. まだなら、最終レビューを通す

subagent-driven-development / executing-plans の途中なら、そのスキルの「Final Review」の手順で出す。
計画なしの作業なら、`requesting-code-review` の `code-reviewer.md` を使って出す。どちらの場合も:

- `subagent_type: reviewer`（`model-policy` ルール）
- 依頼文の冒頭に **「最終ブランチレビュー」** と書く。レビュアーはこれを見て観点表を読む
- 範囲は、既定ブランチからの分岐点〜HEAD（`git merge-base main HEAD`）

報告が返ったら、**「観点ごとの結果」が揃っているかを見る。** 無い・足りないときは、同じレビュアーに
続きを書かせる（最初からレビューを出し直さない）。

指摘の扱いは Superpowers のまま。Critical と Important は修正を1回、その修正の再レビュー
（`re-review-prompt.md`）を1回。残ったものは統括役が裁定し、人に伝える。**全体のレビューを繰り返さない。**

## 3. 印を付ける

**push が通った後、`gh pr create` の直前に**付ける。印は「PR にするコミット」に付くので、
付けた後にコミットが変わると無効になる。

```bash
node scripts/final-review.cjs mark
```

**`gh pr create` とは別のコマンドで実行する。** hook はコマンドを実行する前に判定するので、
1行に続けて書くと、判定の時点では印がまだ無い。

```bash
node scripts/final-review.cjs status   # 今の印を確かめる
```

## 最終レビューの後にコードを変えるとき

push の品質チェックやテストの失敗、人からの依頼など、理由を問わない。

**統括役は直さない。直すのは `implementer` だけ。** 整形や Lint の指摘のような機械的な修正でも同じ。
（人が明示して Native＝`executing-plans` を選んだ作業では、セッション自身が実装者なので、セッションが直す。）

1. 失敗の内容（hook の表示など）をまとめて、`implementer` に1回で渡す。指摘ごとに分けて出さない
2. `implementer` が直し、関係するテストを走らせて、コミットする（畳み方は `submit-pull-request` の手順に従う）
3. 修正の中身を見て、レビューに出すかを決める

   | 修正 | レビュー |
   | --- | --- |
   | 機械的（整形、Lint の自動修正、import の整理、型注釈の追加） | 要らない |
   | 中身がある（処理の流れ・条件・クエリ・入出力が変わる） | `reviewer` に1回見せる |

   **迷ったら見せる。** 見せるときは `re-review-prompt.md` を使い、指摘の欄には失敗の内容を、
   差分には「最終レビューが見たコミット〜今の HEAD」を渡す
4. このレビューで Critical か Important が出たら、`implementer` に1回だけ直させる。
   残りは統括役が裁定し、人に伝える。**レビューは繰り返さない**
5. 送信し直す。品質チェックは hook が走らせる

## 印が要らない PR

ブランチの変更が、ハーネスの配る場所（`.claude/`・`.githooks/`・ハーネスが配る `scripts/` のファイルなど）
だけなら、印なしで通る。ハーネスの取り込みの PR がこれに当たる。何もしなくてよい。

## やってはいけないこと

- **レビューを通さずに印を付けない。** 印は「最終レビューを通し、指摘への対応を終えた」という申告
- **`SKIP_FINAL_REVIEW=1` を、ユーザーの明示的な指示なしに付けない**
- hook に止められたとき、印のファイルを直接書き換えない
- **最終レビューの後の修正を、統括役が自分で直さない。** 1行の修正でも `implementer` に出す

## よくある言い訳

| 考え | 現実 |
| --- | --- |
| 「タスクごとにレビューしたから、最終レビューは済んでいる」 | 範囲も観点も違う。ブランチ全体を、観点表つきで1回通す |
| 「小さい変更だから要らない」 | 小さいかどうかは人が決める。要らないなら、人に `SKIP_FINAL_REVIEW=1` の許可をもらう |
| 「止められた。印を付ければ通る」 | 印はレビューの後に付けるもの。先にレビューを通す |
| 「報告に『観点ごとの結果』が無いが、指摘は無かった」 | 観点表を読んでいない。同じレビュアーに書かせる |
| 「指摘を直したので、もう一度最終レビューを出す」 | 修正の再レビューは1回だけ。全体のレビューを繰り返さない |
| 「Lint の指摘が1件だけ。自分で直したほうが早い」 | 統括役は直さない。`implementer` に出す。早さより、誰が直すかを決めておくことを取る |
| 「テストが通ったから、この修正は見せなくてよい」 | 処理の流れや条件が変わったなら、中身のある修正。レビュアーに1回見せる |
