# テストの原則

どのプロジェクトでも使えるテストの原則。計画でテストの期待を書くとき、最終レビューで観点表の T1 を見るときに読む。
プロジェクトにテスト方針の文書があれば、そのプロジェクトへの当てはめはそちらにある。道具や仕組みが要る備え（期待の一覧と機械の突き合わせ、ミューテーションテスト、認可の表と操作の棚卸しなど）は、プロジェクトが採ると決めたときに当てる。

## 期待の出どころ（テストオラクル）

期待は、次の 5 つの決まりで書く。

1. 期待は設計書から書く。コードから書かない。
2. 設計書に無い振る舞いが要ると分かったら、テストを書く前に設計書を直す。
3. 期待の値は手で導く。テストを先に書き、落ちるのを見てから作る。
4. どのテストにも、暗黙の期待を掛ける。想定外のサーバーの失敗が起きない。応答とログに、書かないと決めたものが出ない。
5. 正しさの期待には、前の結果と比べるだけのテスト（スナップショット）を使わない。

- 実装を読んでテストを書くと、コードのしていることがそのまま期待になり、欠陥があっても欠陥ごと「正しい」として固まる。実装から作るテストは、要件が実装されていない欠落を見つけられない可能性がある。
- 前の結果と比べるだけのテストは、「変わった」は分かるが「正しい」は分からない。

期待の出どころは、次の 4 つを使い分ける。

| 種類 | 何を期待にするか | 使う場面 |
| --- | --- | --- |
| 仕様 | 設計書に書いた決まり | 期待の中心。設計書が正しいことが前提になる |
| 関係 | 何回かの実行のあいだで成り立つ関係。例: 区切って読んだ一覧を最後まで読むと、欠けも重複も無い | 期待の値を 1 つずつ決めにくいとき |
| 暗黙 | どのプログラムでも明らかにおかしいこと | どのテストにも掛ける。期待の値を書かなくてよいので、大量の入力にも使える |
| 人 | 人が見て判断する | 実機の見た目や、使えるかどうか。最後の拠り所で、手間がかかる |

## 場面の選び方

期待を起こすときは、正常系より先に壊し方の分類を当て、加えて仕様からの 4 つの技法を必ず当てる。
- 壊し方の分類（`checklist.md` の T1 の表）は、壊れやすいところの一覧で、経験から場面を選ぶ技法に当たる。条件の組み合わせや状態の移り変わりを漏れなく拾うには、仕様からの技法が要る。

| 技法 | 何をするか |
| --- | --- |
| 同値分割法 | 同じ扱いになる値をまとめ、まとまりごとに 1 つ試す |
| 境界値分析 | まとまりの境目と、その隣を試す。作る人は境目で誤りやすい |
| デシジョンテーブルテスト | 条件の組み合わせを表にして、漏れなく試す |
| 状態遷移テスト | 状態と移り変わりを表にし、許されない移り変わりも試す |

- 技法は、仕様から選ぶ技法（ブラックボックステスト技法）である。仕様から選ぶので、実装が変わっても、求める振る舞いが同じならテストは使える。

プロジェクトは、共通の壊し方の分類に、そのプロジェクトで要る見方を足す。共通の分類は、ある形のアプリから作ったもので、それと違う形のアプリでは薄い見方が残りうるため。

見つかった不具合から分類を見直す。不具合が出たら、どの分類や技法で見つけられたはずかを振り返り、どれにも当たらなければ、分類を足すことを人に提案する（共通の分類はハーネスで、プロジェクトの見方はテスト方針の文書で足す）。分類は長くしすぎない。

- 作る人は同じ誤りを避けることを学ぶので、効かなくなる項目があり、新しく見つかった重い欠陥を映す項目も要る。チェックリストは欠陥の分析に基づいて定期的に更新し、長くなりすぎないようにすべきとされる。

道具に大量の入力を作らせる方法（プロパティベーステスト）は、外から来る文字列を受ける検査の部品に限って使う。

- どんな入力でも成り立つ性質（例: どんな文字列を受けても、想定外のサーバーの失敗にならない）を書き、道具が作る多くの入力で確かめる。

## 段の配分と代役

細かく速いテストを多く、通しの遅いテストは少なくする。手元に本物に近いデータの置き場の模擬があるなら、確かめの中心は、要求を受けるところからその模擬まで通す結合のテストに置く。

- 通しのテストは遅く、画面を変えるたびに直す手間がかかる。細かいテストを多く、上の段ほど少なくする考え方は、テストのピラミッドと呼ばれる。
- 結合のテストなら、認可も、ログの中身も、失敗の場面も、要求を受けるところから通して確かめられ、速い。

本物の代わりに置く部品（代役）は、次のように使う。

- 手元で動く模擬があるものは、代役にせず、模擬をそのまま使う。代役が多いほど、「本物で動くか」から遠ざかるため。
- 例外として、失敗を確かめるときだけ、依存先の呼び出しに失敗を差し込む。依存先が失敗したときの振る舞い（下の「失敗の倒れ方」など）を確かめるため。
- 外のサービスは代役にし、答えの形は本物から写す。節目に本物で確かめる。
- 時刻は差し替えられる作りにする。期限の直前・ちょうど・直後を、待たずに確かめるため。

## 守りを破る側から確かめる

機能のテストは「できるべきことができる」を確かめる。守りのテストは「できてはいけないことができない」を確かめ、期待は「断る」になる。守りは、次の 4 つで確かめる。

| 確かめ | 何をするか |
| --- | --- |
| 認可の表 | すべての操作を、すべての立場で呼び、通すか断るかを確かめる |
| 操作の棚卸し | 登録された操作を数え上げ、認可の表に無い操作があれば落とす |
| 漏れの目印 | テストのデータの秘密に目印を付け、応答とログのどこにも出ないことを、どのテストでも確かめる |
| 失敗の倒れ方 | 確かめの途中で依存先が失敗したとき、通す側に倒れないことを確かめる |

- 認可の問題の多くは、機能を足したり変えたりしたときに、その影響を確かめないことで起きる。操作の棚卸しは、操作を足したのに誰に許すかを決め忘れることを防ぐ。
- レビューはその差分を 1 回読むだけだが、テストは残り、以後の変更のたびに守る。

## 性能

- 端末から見た速さと、サーバーの速さを分けて測る。負荷試験が測るのはサーバーの応答だけで、画面に出るまでの時間は端末で別に測る。
- 回数の枠や費用があるなら、負荷試験は、時間ではなく、送る回数を固定して止める。試験が暴走して、回数の枠や費用を使い切ることを、形で防ぐため。
- 本番と違う手元の環境は、下ごしらえと比べに使う。台本が正しく動くか、前の版より遅くなっていないか、1 回の操作で何回の要求と問い合わせを使うかを確かめる。速さを決めるものが手元と本番で違うので、目標の合否は手元では出さない。
- 件数を増やしても、DB への問い合わせの回数が増えないことを、結合のテストで確かめる。一覧の要素ごとに問い合わせるような作りの悪さは、負荷をかけなくても、毎回の変更で見つけられる。

## テストの質

テストがテストになっているかは、次の 4 つで確かめる。

| 備え | 防ぐもの |
| --- | --- |
| テストを先に書き、落ちるのを見てから作る | 最初から通ってしまうテスト |
| 期待を人が読める一覧に 1 行ずつ番号を付けて書き、その番号とテストを機械で突き合わせて、テストの無い行を出す | 期待はあるのにテストが無い抜け |
| 守りの要の部品（認可の判定、ログインの持ち方、入力の検査など）に、節目にミューテーションテストを掛け、壊してもテストが落ちなかった箇所にテストを足す | テストはあるが、確かめ方が甘い箇所（例: 応答の中身を見ずに「失敗にならないこと」だけを見ている） |
| カバレッジは、通っていない所を見つける道具として使い、数字を目標にしない | 数字を満たすためだけのテスト |

- ミューテーションテストは、道具がコードを 1 か所ずつわざと壊し、そのたびにテストを回す。壊したのにテストが通った箇所が、確かめの甘い箇所である。壊すたびにテストを回すので時間がかかるため、守りの要に絞り、節目に掛ける。
- コードをすべて通っても、判定の組み合わせをすべて確かめたことにはならない。
- 加えて、レビューで、追加・変更した操作ごとに異常系のテストがあるかを見る（`checklist.md` の T1）。
