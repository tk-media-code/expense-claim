# 最終レビューの観点表（脆弱性・性能・テスト）

ブランチ全体を見る最終レビューで、依頼文の観点に加えて使う。依頼文の報告形式はそのまま守り、
その後ろに「観点ごとの結果」を足す。

## 進め方

1. 差分を読み、どの観点が当たるかを決める。当たらない観点は「対象なし」とし、理由を書く
2. 当たる観点は、下の「見ること」を、差分の該当箇所で1つずつ確かめる
3. 判断に必要なら、差分の外も読む。呼び出し先の関数、認証・認可を担う共通の処理、スキーマや索引の定義など。
   読んだ場所は根拠に書く
4. 指摘にするのは、コードで確かめた事実だけ。推測は指摘にせず、確かめてから書く。確かめきれないものは、
   何を確かめれば決まるかを添えて、提案の欄（Recommendations）に書く
5. 元からある問題は、今回の差分が持ち込んだか、悪化させた場合だけ指摘にする。それ以外は提案の欄に書く

「外から来た値」は、リクエスト（パス・クエリ・本文・ヘッダ・Cookie）、アップロードされたファイル、
外部の API の応答、そして DB に保存済みの利用者の入力を指す。

## 重大度

依頼文の3段階に当てはめる。

| 重大度 | 当てはめ方 |
| --- | --- |
| Critical | 外部の人が悪用できる脆弱性（データを盗める・書き換えられる、他人になりすませる、任意の処理を実行できる）。秘密情報の混入 |
| Important | 悪用に条件が要る脆弱性。守りの層が1つ欠けている状態。データの量に比例して悪化する性能の問題（P1〜P3 など）。追加・変更した入口に、当たる分類の異常系テストが無い（T1） |
| Minor | 念のための強化。影響の小さい効率の改善 |

## 脆弱性

### 系統1：外から来た値が命令になる

**V1 SQL・コマンド・コードへの埋め込み**
外から来た値を、文字列の連結や埋め込みで、SQL、シェルのコマンド、`eval` やテンプレートの本体に入れていないか。
プレースホルダや引数の配列など、命令とデータを分ける書き方になっているか。並べ替えの列名のように
プレースホルダにできない箇所は、許可リストから選んでいるか。

**V2 画面への出力**
外から来た値を HTML・属性・スクリプト・URL に出す箇所で、出力先に合ったエスケープが効いているか。
自動のエスケープを外す書き方（生の HTML を差し込む API や、テンプレートの指定）を新しく使っていないか。

**V3 ヘッダ・ログへの埋め込み**
外から来た値を、レスポンスヘッダ（転送先や Cookie）、メールの宛先・件名、ログの行に入れていないか。
入れるなら、改行を通さない作りになっているか。

**V4 入力でファイル・接続先・転送先を決める**
外から来た値で、ファイルのパス、サーバが接続する URL、リダイレクト先を決めていないか。
決めるなら、許可リストで縛っているか。`../` を含む値や、内部のアドレスを指す値で、想定の外へ届かないか。

**V5 外から来たデータの復元**
外から来たデータを、オブジェクトを復元する仕組み（言語が持つ直列化の機能）で読んでいないか。
XML を受け取るなら、外部の実体の参照を無効にしているか。

**V6 入力の検証**
外から来た値の型・範囲・長さ・形式を、サーバ側で検証しているか。画面側の検証だけに頼っていないか。
検証を通らなかった値を、そのまま先へ渡していないか。

### 系統2：「誰が・何を」の確認が抜けている

**V7 認証とセッション**
ログイン、パスワードの再設定、トークンやセッションの発行を変えたとき、試行回数の制限、推測できない ID、
ログイン時の ID の作り直し、Cookie の属性（HttpOnly・Secure・SameSite）が保たれているか。

**V8 認可**
追加・変更した入口（エンドポイント、画面、ジョブ、管理用の機能）のすべてで、「この人がこの対象を操作してよいか」を
サーバ側で確かめているか。ID を変えるだけで、他人のデータに届かないか。ボタンを隠すだけで済ませていないか。

**V9 CSRF とクリックジャッキング**
状態を変えるリクエストに、他のサイトからの送信を防ぐ仕組みが効いているか。その保護を外したり、
対象から除いたりしていないか。画面を他のサイトの枠に入れさせない設定を外していないか。

### 系統3：守るべきデータが漏れる

**V10 秘密情報の埋め込み**
API キー・パスワード・トークン・秘密鍵を、コード・設定・テスト・コメントに書いていないか。
ブラウザへ届くコードや設定に、秘密が入らないか。

**V11 パスワードと暗号**
パスワードは、ソルト付きの遅いハッシュで保存しているか。秘密を守る用途に、弱いハッシュ、自作の暗号、
予測できる乱数を使っていないか。証明書の検証を切っていないか。暗号化されない通信先を足していないか。

**V12 エラー・ログ・レスポンスからの漏えい**
利用者に返すエラーに、内部の情報（スタックトレース、SQL、パス、設定値）を出していないか。
ログやレスポンスに、パスワード・トークン・不要な個人情報を出していないか。

### 系統4：設定と依存物に穴がある

**V13 安全装置を切る設定**
設定ファイル、インフラの定義、CI の定義を変えたとき、デバッグの有効化、CORS の全許可、保護機能の無効化、
セキュリティヘッダや CSP の削除・緩和、公開範囲の広げすぎをしていないか。

**V14 依存ライブラリ**
足した・更新した依存は必要か。名前の似た偽物でないか。ロックファイルと合っているか。
既知の脆弱性は差分からは分からない。専用のコマンドの結果が手元にあれば、それを見る。

### 系統5：機能の作りに穴がある

**V15 ファイルアップロード**
受け取るファイルの種類と大きさを制限しているか。保存先は、公開される場所の外か。
保存する名前を、外から来た値からそのまま作っていないか。

**V16 一括代入**
リクエストの項目を、許可リストなしに、まとめてレコードやモデルへ流し込んでいないか。
権限や所有者のように、利用者に変えさせない項目が書き換えられないか。

**V17 回数・量の制限**
ログイン、認証コードの確認、重い処理、一覧の取得、受け取るデータの大きさに、上限があるか。

**V18 競合状態**
「確認してから更新する」処理（残高、在庫、回数、重複の確認）が、同時に実行されてもすり抜けないか。
確認と更新が、1つのトランザクションか、条件付きの更新にまとまっているか。

**V19 失敗時の倒し方**
検査の途中で例外が起きたとき、通す側に倒れていないか。例外を握りつぶして処理を続けていないか。
途中で失敗したとき、中途半端な状態が残らないか。

**V20 記録**
ログインの成否、権限のエラー、重要な操作に、後から追える記録があるか。

## 性能

**P1 N+1**
一覧やループの要素ごとに、クエリや外部の呼び出しが走っていないか。クエリが呼び出し先の関数の中にある場合や、
関連の遅延読み込みで走る場合も含む。呼び出し先を読んで確かめる。
1件ずつの書き込みを繰り返している箇所は、まとめて処理できないか。

**P2 取りすぎ**
件数の上限やページングなしに、全件を取っていないか。使わない列や関連まで取っていないか。
応答に、使われないデータを詰めていないか。

**P3 索引の効かない検索**
新しい絞り込み・並べ替え・結合が、全件の走査にならないか。スキーマや索引の定義がリポジトリにあれば、
それと照らす。

**P4 計算量**
件数が増えると急に重くなる書き方がないか。入れ子のループでの探索、ループの中での線形の探索や、
重い計算の繰り返しなど。

**P5 I/O の待ち方**
互いに独立した I/O を、1つずつ順に待っていないか。同じデータを、1つの処理の中で何度も取りに行っていないか。
外部の呼び出しに、タイムアウトと、再試行の上限があるか。

**P6 トランザクションの長さ**
トランザクションの中で、外部の呼び出しや、時間のかかる処理をしていないか。

**P7 メモリと資源**
上限なく溜まる配列や一時データがないか。大きなデータを一括で読み込んでいないか。
接続・ファイル・タイマー・購読を、失敗した場合も含めて閉じているか。

**P8 キャッシュ**
キャッシュを足した・変えたとき、結果を左右する入力が、すべてキーに入っているか。
元のデータが変わったときに消えるか。件数か期限の上限があるか。

**P9 画面側**
不要な再描画・再取得をしていないか。長い一覧を、全件そのまま描画していないか。
用途に対して大きすぎる依存を足していないか。

## テスト

**T1 異常系のテスト**
追加・変更した入口ごとに、下の壊し方の分類のうち当たるものに、異常系のテストがあるか。設計で決めた守りを、
破ろうとする側から確かめるテストがあるか（「正しく動く」だけでなく、「破ろうとしても通らない」を書いているか）。
利用者の操作で、想定外のエラー（500）を起こせないか。当たらない分類は「対象なし」と書く。
分類ごとの、そのプロジェクトでの例と期待は、プロジェクトのテスト方針の文書に置く。あればそれと照らし、無ければ下の表の意味から当てる。

| 分類 | 見るもの |
| --- | --- |
| 形の壊れた要求 | 構文や型が合わない入力。必須の部品が無い要求 |
| 文字の端 | 空、空白だけ、上限ちょうどと1つ超え、改行や制御文字、記号、検索の特別な文字 |
| 消えた相手 | 操作の対象や相手が、操作の直前に消えている。一覧の続きを読む目印（次のページの起点）の先が消えている |
| 同時の操作 | 同じ操作の二重送信。同じ対象への同時の更新 |
| 外の失敗 | 依存先（DB、外部のサービス、通信）に届かない。途中で失敗する。想定外の形の応答が返る |
| 悪意 | 他人の資源の指定。改ざんした資格情報。外部への転送先。偽装したファイル |
| 漏れ | 応答とログに、内部の情報（例外の文言、SQL、スタックトレース）や秘密（パスワード、トークン、個人情報）が出る |

## 報告の形式

依頼文の報告（Strengths・Issues・Recommendations・Assessment）をそのまま書き、その後ろに次の節を足す。
見つけた問題は Issues に、依頼文の重大度の区分で書く。

```
### 観点ごとの結果

- V1 SQL・コマンド・コードへの埋め込み：問題なし — 追加したクエリ3件はプレースホルダ（src/repo.ts:10, 42, 88）
- V2 画面への出力：対象なし — 画面への出力を変えていない
- V8 認可：指摘あり — Critical 1
- P1 N+1：指摘あり — Important 2
- T1 異常系のテスト：指摘あり — Important 3
  - 形の壊れた要求：問題なし — 壊れた JSON と型違いのテストがある（tests/post.test.ts:40-88）
  - 文字の端：対象なし — 文字列の入力を足していない
  - 消えた相手：指摘あり — Important 3
  - 同時の操作：対象なし — 確認してから更新する処理を足していない
  - 外の失敗：問題なし — 保存の途中で失敗する場合のテストがある（tests/post.test.ts:120）
  - 悪意：問題なし — 他人の投稿の id を指定する場合のテストがある（tests/post.test.ts:150）
  - 漏れ：対象なし — 応答とログの形を変えていない
（V1〜V20、P1〜P9、T1 のすべてを書く）
```

結果は次の3つのどれか。**30 の観点すべてに、1行ずつ書く。** T1 は、その1行の下に、壊し方の分類ごとの行を7つ足す。

| 結果 | 添えるもの |
| --- | --- |
| 指摘あり | Issues のどの指摘か（区分と番号） |
| 問題なし | 何を見たか。ファイルと行で示す |
| 対象なし | 理由を一言 |

根拠の無い「問題なし」を書かない。見ていない観点を「問題なし」にしない。

実行されるコードも設定も変えていない差分（文書だけなど）では、観点ごとの行の代わりに次の1行でよい。

```
### 観点ごとの結果

- 全観点：対象なし — <理由>
```
