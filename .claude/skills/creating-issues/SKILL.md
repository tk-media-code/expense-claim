# 計画を Issue にして作業を始める

**ここは `writing-plans` と実装のあいだに入る。** プランがあっても Issue が無ければ、
このリポジトリでは実装に入れない（ブランチが切れない）。

## 0. 前の工程を確かめる

**計画がまだなら、先に `brainstorming` → `writing-plans` を通す。**
「小さい変更だから計画は要らない」と判断してよいのは、**人がそう言ったときだけ。**

既に Issue 番号を渡されている場合（「#42 やります」）は、2 を飛ばして 3 へ。

```bash
gh issue view <番号>          # 渡された番号の中身を読む
gh issue list --state open    # 番号が無い場合、既存のものを探す
```

**既にある Issue で足りるなら、それを使う。**新しく作らない。

## 1. 計画から Issue の中身を組み立てる

**プランを要約するのではなく、プランから拾う。** プランには既に、背景・やること・
完了条件に相当するものが書かれている。

| Issue の項目 | プランのどこから取るか |
| --- | --- |
| タイトル | プランの Goal を一文の日本語にする |
| 背景 | **なぜ**この対応が必要か。brainstorming で出た課題・目的 |
| やること | プランの Task をチェックリストにする（1 Task = 1 行） |
| 完了条件 | プランの Goal と、検証が通った状態 |

**Issue にプラン全文を貼らない。** プランは `plans/`（Git 管理外）にあり、Issue は
「何をやるか」を人が読むためのもの。粒度が違う。

## 2. 承認を得てから作る

**勝手に `gh issue create` しない。** 組み立てた4項目をユーザーに提示し、
**「この内容で Issue を作ってよいか」と明示的に聞く。**

意図とずれた Issue が積み上がると、後から読む人が何をやろうとしていたのか追えなくなる。

承認を得たら作る。`.github/ISSUE_TEMPLATE/task.md` の構成に合わせる。

```bash
gh issue create --title "<タイトル>" --body "$(cat <<'EOF'
## 背景

...

## やること

- [ ] ...

## 完了条件

...
EOF
)"
```

**作成された Issue の番号を控える。** 以降の手順で使う。

## 3. 前の作業を片付け、既定ブランチを最新化する

**マージ後の後片付けはここで行う。** Superpowers の `finishing-a-development-branch` が
ブランチを消すのはローカルでマージしたときだけで、PR 経由の作業にはマージ後の手順が無い。
ここは次のブランチを切る直前に必ず通るので、後片付けをここ1か所に置いている。

worktree の中にいると `main` に切り替えられない。まずメインの作業ディレクトリへ移る。

```bash
cd "$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)"
git switch main
git pull --prune
git branch --merged main --format='%(refname:short) %(upstream:track)'
git worktree list
```

`--prune` は GitHub 上で消えたリモートブランチに対応する `origin/…` の追跡参照をローカルから落とす。

**片付けてよいのは、`--merged main` の一覧で末尾に `[gone]` が付いたブランチだけ。**
`main` に取り込まれ、GitHub 上のブランチもマージ時に消えている、つまり PR がマージされたブランチ。
`[gone]` が付いていないものは消さない。コミットがまだ無い作りたてのブランチも `--merged` には
出てくる（別のセッションが作業を始めたばかり、など）。マージしたのに `[gone]` が付かないなら、
GitHub 側の `delete_branch_on_merge` が有効か確かめる。

**そのブランチを worktree で使っていたら、先にその worktree を消す。** worktree で使っている
ブランチは `git branch -d` が拒否する。ただし次のどれかに当たる worktree は消さず、
ブランチも残して人に伝える。

- リポジトリ直下の `.worktrees/` か `worktrees/` の下に無い（`.claude/worktrees/` などはホスト環境の持ち物）
- このセッションを始めたディレクトリである
- `plans/` に、そのブランチに紐付いていないプランがある。`plans/` は Git 管理外なので、
  worktree を消すと中のプランも黙って消える。紐付き先は worktree の中で
  `node scripts/plan-store.cjs status` を実行すると分かる

```bash
git worktree remove <worktree のパス>
git worktree prune
```

**拒否されたら、理由が何であれ `--force`（`-f -f`）も `unlock` もしない。** そこにしか無い
ファイルがあるか、誰かが意図して守っているということなので、中身を見せて人に判断を仰ぐ。
そのブランチも消さずに残す。

```bash
git -C <worktree のパス> status --porcelain -uall
```

ブランチを消す。放っておくとブランチ一覧が読めなくなり、再開時にどれが生きているのか
分からなくなる。

```bash
git branch -d <ブランチ名>
```

**ブランチを消すと、紐付いていたプランも消える。** `.githooks/reference-transaction` が
その場で消し、効いていなくても次のセッション開始時に hook が消す。手で消す必要はない。

`git branch -d` が拒否したら**強制削除しない。** マージコミットで統合する運用なので、
マージ済みなら拒否されない。拒否されたなら何か別の理由がある。

## 4. 作業ブランチを切る

```bash
git switch -c feature/<issue番号>-<内容を表す短い英語>
```

- **接頭辞は `feature/` か `fix/` の2つだけ。** 迷ったら `feature/` に寄せる
- **Issue 番号を必ず含める。** ブランチと Issue の対応が一目で分かるようにするため
- 内容部分は小文字・ハイフン区切りの英語（例 `feature/12-task-read-api`）

**この規約は hook が機械的に検査する。** 外れた名前はブランチ作成の時点で拒否され、
番号が実在しない場合は送信の時点で止まる。

**worktree を使う場合も同じ名前を使う。**

```bash
# using-git-worktrees の手順に乗せるときは、この名前を BRANCH_NAME として渡す
git worktree add .worktrees/feature/<issue番号>-<内容> -b feature/<issue番号>-<内容>
```

## 5. プランをブランチに紐付ける

```bash
node scripts/plan-store.cjs link <ブランチ名> <プランのファイル名>
```

**紐付けるのは今回の作業のプラン**（writing-plans が `plans/` に書いたもの、または
プランモードで確定したもの）。**どのプランかは推測しない。ファイル名を指定する。**
ブランチを作っただけでは、何も紐付かない。

**メインの作業ディレクトリ（手順3で移った場所）で実行する。** worktree の中で実行すると、
その worktree の `plans/` を探してしまい、プランが見つからない。`-> <ブランチ名>` と表示されれば
紐付いている（`node scripts/plan-store.cjs status` でも確かめられる）。どれが今回のプランか
分からないときは、`status` の一覧を見せて人に聞く。

プランは `plans/`（Git 管理外）に置かれ、**紐付けたブランチが消えるまで残る。**
このブランチがマージされ、次の作業の手順3で消えたときに、一緒に消える。

**計画の無い作業（ハーネスの取り込みなど）では紐付けない。** 紐付いていないプランは消えない。

## 6. 報告して実装に入る

ユーザーに「Issue #<番号> / ブランチ `<名前>` で作業を始める」と伝える。

> 完了の目安: Issue が存在し、その番号を含むブランチに居て、`main` の最新が取り込まれていて、
> プランがそのブランチに紐付いている。マージ済みのブランチと、それを使っていた worktree が
> 残っていない（人に伝えて残したものを除く）。

## この先

プランの Execution Handoff で選ばれた方法で実装する。

- Subagent-driven → `subagent-driven-development`
- Native → `executing-plans`

**まだどちらか聞いていなければ、ここで聞く。** 実装が終わったら `submit-pull-request` へ進む。

## よくある言い訳

| 考え | 現実 |
| --- | --- |
| 「小さい変更だから Issue は要らない」 | 小さいかどうかは人が決める。hook はブランチ名しか見ないので、結局切れずに止まる |
| 「Issue はあとでまとめて作る」 | ブランチ名に番号が要る。あとからでは切れない |
| 「承認は取れているはず」 | 「この内容で作ってよいか」と聞いて、返事をもらったか。聞いていないなら取れていない |
| 「プラン全文を Issue に貼れば確実」 | Issue は人が読むもの。プランは `plans/` にある。粒度を混ぜると両方読まれなくなる |
| 「ブランチ名は英語ならなんでもいい」 | `feature/` `fix/` の2つだけ。番号・小文字・ハイフン区切り。hook が弾く |
| 「`--merged main` に出たから、マージ済みとして消してよい」 | 作りたてのブランチも出る。消すのは末尾に `[gone]` が付いたものだけ |
| 「worktree で使っていて消せない。`-D` や `--force` で消す」 | 消してよいのはリポジトリ直下の `.worktrees/` `worktrees/` の下だけ。拒否されたら理由が何であれ人に聞く |
| 「どのプランか分からないので、いちばん新しいものを紐付ける」 | 推測しない。今回のプランのファイル名を指定する。計画の無い作業なら紐付けない |
