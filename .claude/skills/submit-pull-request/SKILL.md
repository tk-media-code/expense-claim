# 変更を送り出す

**マージはしない。PR を作ったら止まる。**

`finishing-a-development-branch` から渡ってくる工程。このリポジトリで採れる統合は
Pull Request の1本だけなので、ローカルで `main` にマージする経路は使わない。

## 1. 何が出ていくのかを確かめる

```bash
git status
git diff
git log --oneline main..HEAD
```

**意図した変更だけが入っているか**を確認する。意図しないファイル（ローカル設定、
デバッグ用の一時ファイル、生成物）が混ざっていないか見る。

## 2. コミットする

書式は `commit-and-pr` ルールに従う。**件名は日本語・常体・「〜する」で終える。**

```bash
git add <ファイル>
git commit -m "$(cat <<'EOF'
<件名>

<なぜこの変更が必要か。判断の根拠。採らなかった案があればその理由も。>

Closes #<issue番号>

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
EOF
)"
```

**本文には「なぜ」を書く。** 何を変えたかは差分を見れば分かる。差分から読み取れないのは
判断の根拠のほうなので、そこを残す。

## 3. 最終レビューが済んでいるかを確かめる

**PR を作る前に、ブランチ全体の最終レビューが1回要る。** `final-review` スキルの 1〜2 に従う。
（ブランチの変更がハーネスの配る場所だけなら、最終レビューも印も要らない。手順5を参照）

- 済んでいれば、次へ進む
- まだなら、ここで通す。指摘の修正は `implementer` に出し、コミットしてから次へ進む

**タスクごとのレビューは、最終レビューの代わりにならない。** 計画なしの作業でも、ここで1回通す。

## 4. 送信する

```bash
git push -u origin <ブランチ名>
```

**既定ブランチへは送らない。** 作業ブランチをそのまま送る。

送信の前に、そのブランチ名が `feature/<issue番号>-<内容>` の形になっていることを確かめる。
番号が実在しないブランチは共通チェックが止める。

**品質チェックを手で叩かない。** 送信を検知した hook が `scripts/harness-check.cjs` →
`scripts/quality-check.cjs`（または `.sh`）の順に自動で回す。先に手で実行しても同じものが2回走るだけ。

失敗すると**送信そのものがブロックされる。** リモートには何も出ていない。

**統括役は、指摘を自分で直さない。** 失敗の内容をまとめて `implementer` に渡し、直させる
（`final-review` スキルの「最終レビューの後にコードを変えるとき」）。整形や Lint の指摘でも同じ。
人が明示して Native を選んだ作業だけは、セッション自身が直す。

`implementer` が直したら、修正の中身を見て `reviewer` に見せるかを決め（`final-review` スキルの同じ節の手順3。迷ったら見せる）、
まだ送信できていないコミットに畳ませてから、送信し直す。

```bash
# implementer が指摘を修正してから
git add <ファイル>
git commit --amend --no-edit
git push -u origin <ブランチ名>
```

**送信済みのコミットは `--amend` しない。** force push が要るうえ `permissions.deny` で禁止
されている。その場合は修正を新しいコミットとして積む。

**指摘が0件になるまで、この手順を繰り返す。** 安易に作業を止めたり、
ユーザーに丸投げしたりしない。

ブロックを回避する `SKIP_QUALITY_CHECK=1` を、**ユーザーの明示的な指示なしに付けてはならない。**
誤検知やチェック自体の不具合を疑うときは、まずユーザーに状況を説明して判断を仰ぐ。

## 5. 印を付ける

送信が通ったら、PR を作る直前に、最終レビューの印を付ける。

```bash
node scripts/final-review.cjs mark
```

**`gh pr create` とは別のコマンドで実行する。** hook はコマンドを実行する前に判定するので、
1行に続けて書くと、判定の時点では印がまだ無い。

印は「最終レビューを通し、指摘への対応を終えた」という申告。**レビューを通さずに付けない。**

次の場合は、印は要らない（hook も求めない）。

- ブランチの変更が、ハーネスの配る場所だけ（ハーネスの取り込みなど）
- `scripts/final-review.cjs` が配られていないリポジトリ

## 6. PR を作る

```bash
gh pr create --title "<件名>" --body "$(cat <<'EOF'
## 概要

<何を・なぜ変更したか>

Closes #<issue番号>

## 変更内容

- ...

## 確認事項

- [x] ブランチ名にIssue番号を含めている
- [x] 品質チェックを通している
- [x] 最終レビュー（脆弱性・性能・テストの観点つき）を通している
- [ ] 動作確認済み
EOF
)"
```

**`Closes #<issue番号>` を本文に必ず含める。** これが無いとマージしても Issue が閉じない。

**印が無いと、hook が `gh pr create` を止める。** 止められたら、`final-review` スキルの手順へ戻る。
印なしで通した場合（配布物だけ／ユーザーの許可で `SKIP_FINAL_REVIEW=1`）は、
「最終レビュー」の行にチェックを付けず、理由を書く。

## 7. ここで止まる

**`gh pr merge` は実行しない。** マージはユーザーが内容を確認した上で行う。

PR の URL をユーザーに伝え、**確認とマージを依頼して終わる。**

> 完了の目安: PR が作られ、その URL をユーザーに渡している。**マージはしていない。**

## この先

マージの報告を受けても、後片付けのために動かなくてよい。マージ済みのブランチと worktree は、
次の作業で `creating-issues` がブランチを切る直前（手順3）にまとめて片付ける。
