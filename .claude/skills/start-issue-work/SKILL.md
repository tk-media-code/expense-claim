# 作業を始める

実装依頼を受けたら、**コードに触る前に**この手順を通す。

## 1. 対象の Issue を確かめる

**依頼に Issue 番号があるか**を見る。

```bash
gh issue view <番号>          # 番号を渡された場合
gh issue list --state open    # 番号が無い場合、既存のものを探す
```

**既にある Issue で足りるなら、それを使う。**新しく作らない。

## 2. Issue が無ければ起案して承認をもらう

**勝手に `gh issue create` しない。** 次の4項目をユーザーに提示し、**承認を得てから**作る。

| 項目 | 中身 |
| --- | --- |
| タイトル | 何をするのかが一目で分かる短い日本語 |
| 背景 | **なぜ**この対応が必要か（きっかけ・課題・目的） |
| やること | 対応内容のチェックリスト |
| 完了条件 | どうなったら「完了」と言えるか |

**「この内容で Issue を作ってよいか」と明示的に聞く。** 承認なしに作らない。
意図とずれた Issue が積み上がると、後から読む人が何をやろうとしていたのか追えなくなる。

承認を得たら作る。`.github/ISSUE_TEMPLATE/task.md` の構成に合わせる。

```bash
gh issue create --title "<タイトル>" --body "$(cat <<'EOF'
## 背景

...

## やること

- [ ] ...

## 完了条件

...
EOF
)"
```

**作成された Issue の番号を控える。** 以降の手順で使う。

## 3. 既定ブランチを最新化し、後片付けをする

```bash
git switch main
git pull --prune
git branch --merged main    # マージ済みで不要になったローカルブランチを確認
```

`--prune` は GitHub 上で消えたリモートブランチに対応する `origin/…` の追跡参照をローカルから落とす。

マージ済みのブランチがあれば削除する（`main` 自身は除く）。放っておくとブランチ一覧が
読めなくなり、再開時にどれが生きているのか分からなくなる。

```bash
git branch -d <マージ済みブランチ>
```

## 4. 作業ブランチを切る

```bash
git switch -c feature/<issue番号>-<内容を表す短い英語>
```

- **接頭辞は `feature/` か `fix/` の2つだけ。** 迷ったら `feature/` に寄せる
- **Issue 番号を必ず含める。** ブランチと Issue の対応が一目で分かるようにするため
- 内容部分は小文字・ハイフン区切りの英語（例 `feature/12-task-read-api`）

**この規約は `scripts/harness-check.sh` が機械的に検査する。** 外れていると送信時に止まる。

## 5. プランをブランチに紐付ける

プランモードで計画を立ててからここへ来た場合、そのプランを今のブランチに結びつける。

```bash
node scripts/plan-store.cjs link <ブランチ名>
```

プランは `plans/`（Git 管理外）に置かれ、**紐付けたブランチが消えるまで残る。**
マージ後の後片付けでブランチを消したとき、`sync-after-merge` が一緒に片付ける。

`.githooks/reference-transaction` が効いていれば、ブランチを切った時点で自動的に
紐付いている。**そのときこのコマンドは何もしない（冪等）ので、そのまま実行してよい。**

## 6. 報告して実装に入る

ユーザーに「Issue #<番号> / ブランチ `<名前>` で作業を始める」と伝えてから実装する。

> 完了の目安: Issue が存在し、その番号を含むブランチに居て、`main` の最新が取り込まれている。

## この先

作業が終わったら `submit-pull-request` スキルへ進む。**自分でマージはしない。**
