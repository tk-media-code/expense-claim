# 設計

要件定義（[`docs/requirements.md`](../requirements.md)）で決めた「何を満たすか」を、
**どう作るか**へ落とした文書を置く。

## 読む順番

| # | 文書 | 何を決めるか | 状態 |
| --- | --- | --- | --- |
| 1 | [`architecture.md`](architecture.md) | 技術選定、システム構成、層の分け方、認可情報の扱い | **作成済み** |
| 2 | [`screens.md`](screens.md) | 画面遷移、画面項目定義、状態と分岐 | **作成済み** |
| 3 | [`database.md`](database.md) | 物理 ER 図、テーブル定義、型・索引・制約 | 未着手 |
| 4 | [`api.md`](api.md) | フロントとバックの間のエンドポイント | 未着手 |
| 5 | [`integration.md`](integration.md) | Gmail / ドライブ / スプレッドシートの呼び出し設計、OAuth フロー | 未着手 |
| 6 | [`error-handling.md`](error-handling.md) | 異常系の実現方法、要確認事項の発生経路 | 未着手 |

**1 から順に決まっていく。** 後ろの文書は前の文書の結論を前提にしている。

## 書き方の約束

要求分析・要件定義と同じ流儀で書く。

- **決めたことには要件の番号を添える**（`F-xx` / `NF-xx` / `R-xx` / `N-xx`）
- **採らなかった案と却下理由を残す。** 後から同じ検討を繰り返さないため
- **推測と実測を区別する。** 実機で確かめていないことは「未検証」と明記する
- **このリポジトリは public。** スプレッドシートID・シート名・フォルダID・会場コードの実値・
  氏名・メールアドレスを書かない（N-08 / N-18）。例示は架空の値を使う

## 図の描き方

**Mermaid を正本にする。** GitHub が markdown の中でそのまま描画し、
**PR で差分が読める。** ER 図は `erDiagram`、画面遷移とシステム構成は `flowchart` を使う。

`.drawio` 形式は座標を持つ XML で、**PR で差分が読めない**ため正本には置かない。
