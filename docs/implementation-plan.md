# 実装計画

設計（[`docs/design/`](design/)）で決めた「どう作るか」を、**どの順で、どの粒度で作るか**へ落とす。
**実装タスクの一覧と進捗を、この1枚に集める。**

## 1. この文書について

| | |
| --- | --- |
| **扱うこと** | 実装タスクの一覧・粒度・順序と、**いまどこまで進んだか** |
| **扱わないこと** | **何を作るか**（設計書7本が正本）／**なぜそう決めたか**（[`decisions.md`](decisions.md)）／**どう起動しどう品質を保つか**（[`07-development.md`](design/07-development.md)） |
| **出どころ** | [`02-screens.md`](design/02-screens.md) の11画面、[`03-database.md`](design/03-database.md) の16テーブル、[`04-api.md`](design/04-api.md) の37エンドポイント |
| **更新の仕方** | **各タスクの実装 PR が、その行の `Issue` 列と `状態` 列を書き換える**（5章） |

### この文書が要る理由

設計は実装できる粒度まで降りているが、**残量を横断して見る手立てが無かった。**
進捗に相当する情報は [`design/README.md`](design/README.md) の「読む順番」表・
[`decisions.md`](decisions.md)・各設計書の「未確定事項」章（8箇所）に分散していて、
**実装が何割終わったのかはどこを見ても分からない。**

**この表が答えるのは2つだけである。**

1. **いまどこまで進んだか**（3章のサマリ）
2. **次に何をやるか**（4章の、上から最初の `⬜`）

## 2. 進め方の約束

### 2.1 粒度と順序

| 約束 | なぜ |
| --- | --- |
| **1タスク = 1 Issue = 1 PR** | 差分を最小にし、**1回のレビューで理解が追いつく**状態を保つ。既存の直列運用（Issue 42件・PR 40件）をそのまま延長する |
| **フェーズ内は DB → BE → FE の順** | **データの形が先に決まらないと、API も画面も書き直しになる。** 層ごとに区切ると、どこを読めばいいかも分かれる |
| **フェーズは簡単な順** | 外部連携の無い CRUD から始め、**認証・Google API・提出は後ろへ回す。** 難しいものが先に来ると続かない |
| **1 PR の差分は 300 行を目安に収める** | 超えるならタスクを割る。**割ったら4章の表に行を足す** |
| **表の更新は実装 PR に含める** | 進捗の更新だけのコミットを作らない。**`main` は常に真である** |

**表の行に着手するときは [`start-issue-work`](../.claude/skills/start-issue-work/SKILL.md) を通す。**
行のタイトルをそのまま Issue のタイトルにし、背景・やること・完了条件を起案して承認を得る。

### 2.2 依存で動かせない3箇所

**「簡単な順」を優先するが、次の3つだけは依存が勝つ。**

| 制約 | どう置いたか |
| --- | --- |
| 駅の削除は「使っている区間が無いとき」だけ（F-15 / 決定22） | `segments` を**駅の削除 API より前**に置いた（`1-2` → `1-4`） |
| 月度切替の実績削除は「**提出が済んだ**月度」を判定する（F-32） | `submissions` が要るので、同期の Phase 9 ではなく **Phase 11** に置いた（`11-8`） |
| Phase 8 以降が要確認事項を積む（[`06-error-handling.md`](design/06-error-handling.md) 3章） | `attentions` を **Phase 7** で先に作る |

### 2.3 段階的に育つエンドポイントが3本ある

**一度で完成しない。** 後のフェーズで項目が増える。表の該当行に印を付けてある。

| エンドポイント | どう育つか |
| --- | --- |
| `GET /api/home` | Phase 3 で案件一覧 → Phase 4 で記録の済み／未 → Phase 7 で未確認件数 → Phase 11 で提出状態 |
| `GET /api/projects/:id/expense-record` | Phase 4 でルートと記録 → Phase 10 でタクシー乗車 |
| `POST /api/sync` | Phase 9 で取り込み → Phase 11 で月度切替の検知 |

### 2.4 採らなかった案

| 案 | 却下理由 |
| --- | --- |
| **GitHub Projects のボード** | この環境の `gh` が 2.4.0 で `gh project` サブコマンドが無く、トークンにも `read:project` が無い。**AI が読み書きできない。** 使うには gh のアップグレードとスコープ追加が要る |
| **マイルストーン ＋ ラベル** | Issue 42件・PR 40件を回してきて**一度も使っていない。** いま入れても、**横断して残量を見る表にはならない** |
| **`plans/` に置く** | `plans/.gitignore` が `*` で自己 ignore しており、**紐付いたブランチが消えると `plan-store.cjs gc` が消す。** 進捗の正本を置けない |
| **各設計書の「未確定事項」を流用する** | あれは**設計上の宿題**であって実装の残量ではない。**8箇所に分散していて合計が出ない** |
| **`🟡 作業中` を状態に持つ** | 1タスク = 1 Issue なので、**作業中かどうかは「開いている Issue」がそのまま示す。** 表に持つと着手時と完了時で同じ行を2度書き換えることになり、**しかも `main` 上では PR が一度にマージされるので `🟡` が現れる瞬間が無い。** 台帳を二重に持たない |

## 5. この表の更新の仕方

**進捗の更新だけのコミットを作らない。** 実装 PR の中で、その行を書き換える。

| いつ | 何を |
| --- | --- |
| **Issue を採番したとき** | 4章の該当行の `Issue` 列に `#83` の形で入れる |
| **実装が終わったとき** | `状態` を `✅` にし、3章のサマリの進捗バーと分母・合計を数え直す |
| **タスクを割ったとき** | 4章に行を足し、3章の分母と合計を直す。**番号は `1-3a` のように枝番で足し、既存の番号は動かさない** |
| **Phase を終えたとき** | その節の下に `> **Phase N は閉じた**（日付 / Issue #N）` を1行残す |

**進捗バーは10目盛りである。** 埋まった数は `round(完了 / 全体 × 10)` で、`█` と `░` を並べる。

**作業中のタスクは、この表には出ない。** 1タスク = 1 Issue なので、
**開いている Issue がそのまま「いま誰かが触っているもの」である。**
