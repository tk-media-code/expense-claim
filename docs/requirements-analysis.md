# 交通費精算アプリ 要求分析

## 1. この文書について

この文書は、交通費精算アプリを **なぜ作るのか**・**何が欲しいのか** を、依頼者本人の言葉に沿って
整理したものである。要件定義（`docs/requirements.md`、今後作成）の手前に置く。

- **扱うこと** — 現状の困りごと、実現したいこと、やらないこと、まだ決まっていないこと
- **扱わないこと** — 画面設計、データ構造、技術選定、実装方式。これらは要件定義以降で決める
- **出どころ** — 依頼者本人へのヒアリング（口述および確認質問）と、
  提供された実物（提出先スプレッドシート、依頼メール）の解析、および
  **提出シートを Sheets API / Drive API から直接読み書きした実測**（`tools/sheet-probe/`）と、
  **依頼メールを Gmail API から直接読んだ実測**（`tools/gmail-probe/`）、
  さらに **本人が提出シートへ実際に記入した内容の実測**（2026-08-31）
- **更新の仕方** — 「10. 未確定事項」が埋まったらこの文書を直す。要件定義の途中で要求がひっくり返った
  場合も、**なぜひっくり返ったか**を添えてここへ書き戻す

> **このリポジトリは public である。**
> 実物には他スタッフの氏名・メールアドレス、実在のご両家名、会場名、緊急連絡先などが含まれる。
> **この文書には構造と仕様だけを書き、実データは書かない。**
> スプレッドシートID・シート名・フォルダID・会場コードの実値といった環境依存値は
> `.env` で管理する（`.gitignore` は `.env` を除外済み）。

## 2. 背景

- 依頼者は **結婚式のビデオグラファー**。企業からの業務委託を受け、結婚式場で結婚式の動画を撮影している
- 稼働日は主に **土日と祝日**。**ブライダル業界は土日祝が休みではない**ため、
  祝日が平日にあたる日でも撮影は発生する。**委託元も祝日に稼働している**（本人談・2026-09-04）
- 撮影業務の依頼は **メール** で届く。委託元専用の Gmail ラベルに振り分けられており、
  そのラベルには **案件詳細メールと「依頼無し」の連絡メールの2種類**が来る
- **依頼メールは月曜に届く。** それ以降に届くものはシフト変更などが起きた場合で、
  依頼の形としてはイレギュラーにあたる。**月曜が祝日でも配信は行われる**（本人談・2026-09-04）
- **1回の配信が覆うのは、その週の稼働日と、それに連なる月曜の祝日である**（本人談・2026-09-04）。
  土日に月曜の祝日が連なる3連休では、**その月曜ぶんも同じ回に含まれる。**
  9/5（土）・9/6（日）・9/7（月）に撮影が入り 9/7 が祝日だったとすれば、
  **3件とも 8/31（月）に届く**
- **「前の週に届くことはない」は成り立たない。** 当初はそう書いていたが（本人談・2026-09-01）、
  **祝日を考慮に入れた時点で崩れた。** 月曜祝日の施行分は、前の週の月曜に届く
- **実測で裏が取れているのは、祝日を含まない通常週の1週ぶんだけ**（6章。2026-08-31 の月曜に、
  その週の土日ぶんが届いていた）。**月曜祝日の回は未実測**（10章）
- アカウントは移行期にある。従来は個人の Gmail アカウントを使っていたが、
  **独自ドメインを取得して Google Workspace での運用を始めた**。委託元には独自ドメインのアドレスを
  伝えており、**現在はどちらのアカウントからも提出シートを閲覧・編集できる状態**
- **依頼メールの送信先は、独自ドメインへ切り替わった**（2026-08-31 に着信を確認）。
  個人の Gmail には届かなくなった。**Gmail を読む機能（R-01）は実データで検証済み**（6章）
- **ただし、届いたメールにラベルは付いていなかった。** 委託元がラベルを付けているのではなく、
  **自分の Gmail フィルタが付けている**。Workspace 側にフィルタを作っていなかったため、
  最初の2通はラベルが無いまま届いた（あとから差出人アドレスを条件にフィルタを作って付けた）
- 依頼メールをもとに仕事を受注し、受注した案件ごとに交通費が発生する
- **案件は月に6〜10件。** 1案件が乗り換えのぶんだけ行を増やすため、
  提出シートで使える25行（5.3）に収まるが余裕は少ない
- **受注した案件が後から無くなることがある。** 依頼の辞退、受注後のキャンセル、
  日程や会場の変更のいずれも起きる
- **前月分の交通費を委託元へ提出する。提出期限は翌月3日正午。**
  提出形式は委託元が用意した Google スプレッドシート
- **提出後、委託元から差し戻しや修正依頼がまれに来る**
- 精算する交通費は **公共交通（電車・バス）** と **タクシー** の2つ
- 現場までの経路は会場ごとに固定ではない。単純な1区間のこともあれば、途中駅で乗り換えることもあり、
  **同じ会場でも複数の行き方がある**
- タクシーに乗るかどうかも事前には決まらない。
  **その日にどの経路を使ったかが確定するのは、1日の終わり**である

**依頼が届く時期から、毎月かならず月をまたいで案件を持つ期間が生まれる。**

依頼が月曜にしか届かないということは、**月初（1〜7日ごろ）の案件は前月末に届く**
ということである。**これは実際に起きている。** 9/5（土）・9/6（日）ぶんの連絡が
**8/31（月）に届いていた**（6章・API 実測）。

| | |
| --- | --- |
| 依頼から稼働までの猶予 | **最長7日**（月曜に届いて、翌週の月曜が祝日ならその日に施行）。祝日の絡まない週は最長6日。イレギュラーでは当日まで詰まる |
| 前月中にアプリへ入る翌月分 | **翌月第1週（1〜7日）の施行分だけ。** それより先の案件は入ってこない |

**「翌月第1週まで」は計算で出る。** 配信は月曜 M で、覆う最も遠い日はその翌週の月曜（M+7）である。
M が前月に属する最後の月曜なら、**M は前月の末日から6日以内**にあり、
したがって **M+7 は翌月1日から7日のあいだ**にしかならない。月の日数によらずそうなる。

> **これは連休が月曜までの場合である。** 火曜以降まで連なる連休（シルバーウィークなど）が
> 月初に来たときに配信の範囲がどこまで伸びるかは、**確かめていない**（10章）。

**これが「案件がどの月度に属するか」を決めておかなければならない理由である**（N-20）。
月度の切替期間（翌月4〜7日・5.4）は、**まさにこの翌月第1週の稼働日と重なる。**

## 3. 現状の業務フロー（As-Is）

1. **依頼を受ける** — 委託元から撮影依頼のメールが Gmail に届く。
   自分で作ったフィルタが委託元専用のラベルへ振り分けており、
   同じラベルに「依頼無しのご連絡」も来るので、案件かどうかを自分で見分けている。
   **届くのは月曜で、稼働までの猶予は最長7日**（2章）
2. **受注する** — 依頼を受けることを決め、撮影日・会場・ご両家名が確定する
3. **稼働する** — 現場へ向かい、撮影し、帰る。行き帰りの経路とタクシー利用の有無は、この日に確定する
4. **覚えておく** — 使った経路・運賃・タクシー代を、提出まで自分で覚えている、あるいは控えておく
5. **月初にまとめて手入力する** — 提出シートの自分のシートに、前月分をすべて手で書き写す
   - 日付・会場コード・目的・ご両家名
   - 出発駅・到着駅・往復か片道か・金額
   - タクシー代
   - **乗り換えがある場合は、区間ごとに行を分けて書く**
6. **領収書を処理する** — タクシーに乗った分は、領収書を Google ドライブに保管し、
   **その Drive の URL を提出シートの領収書欄に書く**。これも手作業
   - 保管先は **1つのフォルダにまとめている**。月ごとには分けていない
   - 委託元が開けるよう、**「リンクを知っている全員が閲覧可」で共有している**
   - **その共有はファイル単位で付いている。フォルダには付いていない**（API 実測）。
     フォルダ自体は非共有のままで、中の各ファイルに `anyone / reader` が個別に付いている（N-19）
   - **保管先は Workspace 側へ移った**（2026-08-31 実測）。以前は個人アカウント側にあり
     この文書にもそう書いていたが、アカウントの移行にあわせて移された
   - **ファイル名は配車アプリが付けた名前のまま**使っている
     （`<サービス名>領収書_<YYYYMMDD>_<HHMM>.pdf` の形）

## 4. 現状の課題

**(1) 入力がすべて手作業で、量が多い**

日付・会場・目的・ご両家名・区間・金額・タクシー・領収書。1案件ごとにこれだけの項目を、
月初にまとめて手で書き写している。

**(2) 思い出しコストがかかる**

経路とタクシー利用が確定するのは稼働日当日。しかし入力するのは月初。
**確定した時点と記録する時点が最大1か月離れている**ため、月初の作業は「あの日はどう行ったか」を
思い出すところから始まる。

実際、**ある日に乗ったタクシーの領収書がドライブに上がったのは、8日後だった**（API 実測）。

**(3) 入力したい場所と、入力できる場所がずれている**

経路が確定するのは現場からの帰り道である。だが現状の入力先は PC 前提のスプレッドシートで、
その場では入力できない。結果として、記憶か手控えに頼るしかない。

**(4) 経路を決め打ちにできないので、定型化もできない**

「この会場ならこのルート」と固定できれば定型化できるが、同じ会場でも複数の行き方があり、
どれを使ったかは当日にならないと決まらない。そのため毎回ゼロから書くことになる。

**(5) 乗り換えのぶんだけ行が増える**

提出シートは **1行 = 1区間**という粒度で、乗り換えるたびに行を分ける必要がある。
1案件が複数行になるため、手入力の量は案件数以上に膨らむ。

**(6) 領収書の扱いが手数を増やしている**

タクシー分は、領収書をドライブに置き、その URL をコピーしてセルに貼る、という別作業が発生する。

## 5. 提出先スプレッドシートの仕様

Excel 形式でダウンロードした実物の解析に加え、**Sheets API と Drive API で実物を直接読んで
確かめた**構造（2026-08-29 実施）。

> **xlsx から読み取った内容には、変換で歪んだものが混じっていた。**
> **「API 実測」と書いた項目が正**である。歪みの実例と原因は 5.3 に残す。

### 5.1 ブックの構成

- **1つの共有ブックに116シート（うち非表示20枚）。スタッフ1人につき1シート**という作り（API 実測）
- 自分のシートは、シート名が `<社員番号> <氏名>` の形式
- **社員番号は数字だけとは限らない。** `P1003` `S1003` `H08` のように英字が前に付くものがある（API 実測）
- 共通シートは「ルール」「交通費一覧」「会場」「入力例」「参考」の5枚（API 実測）
- 会場マスタは43件。**3文字前後の英数字コード**で管理されている
- ブックのロケールは `ja_JP`、タイムゾーンは `Asia/Tokyo`（API 実測）
- ファイルの所有者は委託元。自分の権限は**編集可・複製可・共有可・削除不可**（API 実測）
- **共有は「リンクを知っている全員が編集可」で付いている**（API 実測）。
  個別の招待は14件しかなく、スタッフ91名の大半はこのリンク共有でアクセスしている。
  **独自ドメインのアカウントも個別には招待されていない**（N-13 参照）

### 5.2 自分のシートの構造

- **シートの実サイズは 33行 × 13列。固定行は7行**（API 実測）
- 保護範囲は2つあり、**1〜7行目は編集できず、8〜32行目には自分の編集権が与えられている**（API 実測）
- 合計欄（4行目の `H4` `I4` `J4` `K4` `L4`）には数式が入っており、**触ってはいけない**

| 保護範囲 | 自分が編集できるか |
| --- | --- |
| 1〜7行目 | **できない** |
| 8〜32行目 | **できる** |

7行目がヘッダー、8行目からデータ。

| 列 | 項目 | 入力規則 |
| --- | --- | --- |
| A | 日付 | 日付形式のみ |
| B | 目的地(会場) | プルダウン。会場マスタの範囲を参照する |
| C | 目的 | プルダウン（婚礼案件／婚礼以外／営業／顧客打合／DP打合／通勤／その他） |
| D | 案件名(新郎/新婦) | 自由入力。`〇〇様△△様` の形式 |
| E | 出発駅 | 自由入力 |
| F | 到着駅 | 自由入力 |
| G | 往復 | プルダウン（往復／片道） |
| H | 金額 | 0以上の数値。電車・バスの運賃 |
| I | タクシー | 0以上の数値 |
| J | 高速代/駐車場 | 0以上の数値。**使わない** |
| K | 車両 | 自家用車移動費・承認者のみの欄。**使わない** |
| L | 備考 | 自由入力 |
| M | 領収書 | **M8:M32 が丸ごと1つの結合セル。** ここに Drive の URL を書く |

**1行 = 1区間**（出発駅・到着駅のペア＋往復/片道）という粒度になっている。

#### 記入の実際

**本人が記入した内容を読んで確かめた**（2026-08-31 実測）。
列の意味だけでは決まらない、**実際の書き方**がここで分かった。

| 分かったこと | 中身 |
| --- | --- |
| **乗り換え行は A〜D列を空にする** | 1案件が複数行になるとき、2行目以降に日付・会場・目的・案件名を**繰り返さない**。E〜H列（出発駅・到着駅・往復・金額）だけを書く |
| **タクシー代は専用行を立てない** | 電車の区間行の I列に相乗りさせる。タクシーだけの行は作らない |
| **I列はその日のタクシー代の合計** | 1日に複数回乗っても金額は1つにまとめる（本人確認済み）。領収書は乗車ごとに残る（R-12）ので、**乗車の数と行の数は一致しない** |
| **H列は往復の合計額** | G列が「往復」のとき、H列には往路と復路を合わせた額が入る（本人確認済み）。片道運賃ではない |
| **駅名は鉄道会社の略称付き** | `<社名><駅名>` の形で書く。**乗換駅は会社ごとに別の駅として書かれる**ため、社名を落とすと同じ駅に見えてしまう |
| **C列は全行「婚礼案件」** | ヒアリングどおり。実データで裏が取れた |
| **G列は全行「往復」** | 片道の実例は無い。R-08 の「往路・復路を別々に指定」は、あってよいが実績の無い機能 |
| **J・K・L列は空** | 高速代/駐車場・車両・備考。9章で対象外としたとおり |

**この書き方は、検証スクリプトが試した書き方とは違う。**
`tools/sheet-probe/probe.cjs` の段階B-g（R-08 の確認）は、乗り換えの2行目にも日付・会場・目的・
案件名を書いている。**書けること自体はそれで確かめられたが、本人の書き方はそうではない。**
提出シートへ書き出すときは、**2行目以降の A〜D列を空にする。**

**領収書欄は行ごとに書き分けられない（API 実測）。** M8:M32 が単一の結合セルであり、
**1か月あたり1枠しかない。** ヘッダーの文言も「領収書はこちらに添付してください」。

**ただしこれは支障にならない。** 委託元の担当者が文字列として読めればよく、
**その月の URL を改行で区切って1つのセルに並べる**方式で運用できる（本人に確認済み）。
容量にも余裕がある。

| | 実測値 |
| --- | --- |
| M列の幅 | 577px。Drive の URL は 10pt で約446px なので1行に収まる |
| 結合セルの高さ | 625px（8〜32行の合計）。10pt なら40行以上並べられる |
| 折り返し設定 | `OVERFLOW_CELL`。ただし**明示的な改行は設定に関係なく行が分かれる**ので問題ない |

**M列は最終列（13列目）で、はみ出した分の逃げ場が無い。**
1行が577pxを超えると視覚的に切れるため、1行に1つの URL だけを置くこと。

**実際の書き方は「日付の見出し + URL」だった**（2026-08-31 実測）。
その日のぶんをまとめて、次の形で並べている。

```text
(M/D)
<1件目の Drive URL>
<2件目の Drive URL>
```

**乗車が複数回あれば URL も複数行になる。** 日付の見出しがあるので、
担当者はどの行のタクシー代に対応する領収書かを追える。

**委託元が想定している添付方法は、これとは別である。**
ブック内の「入力例」シートには、次の手順が書かれている。

> ＜領収書添付＞PCでの操作
> 1. 領収書貼付欄を選択し、「挿入」→「画像」→「セル上の画像」の順にクリック
> 2. 「アップロード」→「参照」順にクリックし、領収書画像を添付

**委託元は画像の直接添付を想定しており、Drive の URL ではない。**
現行運用が URL 方式であることは本人に確認済みで、実際にそれで回っている。
そのうえ **Sheets API には「セル上の画像」を挿入するリクエストが無い**ため、
アプリが採れるのは URL 方式だけである（9章）。
※これは API の仕様から言えることで、**実機では試していない**。

**他人のシートは編集できない。ただし2枚だけ例外がある（API 実測）。**
委託元側の保護設定の不備と見られる。**アプリはいかなる場合も他人のシートへ書かない。**

| シート | 自分が編集できてしまう範囲 |
| --- | --- |
| 社員番号 1050 | 8〜19行の A〜H列 |
| 社員番号 1062 | 1〜7行（ヘッダー） |

### 5.3 入力できる行数

**8〜32行目の 25行。ただし自分で行を挿入すれば増やせる**（API 実測）。

| 調べたこと | 結果 |
| --- | --- |
| 保護範囲 | **8〜32行目に自分の編集権がある。** 1〜7行目には無い |
| グリッドの実サイズ | 33行 × 13列。**34行目以降は存在せず、書こうとすると `400 Range exceeds grid limits` で拒否される** |
| 入力規則の範囲 | `A8:A32` `B8:B32` `C8:C32` `G8:G32` `H8:H32` `I8:I32` `J8:J32` `K8:K32` |
| 合計式 | `H4 = if(sum(H8:H),sum(H8:H),)` のように **範囲が閉じていない**。I4・J4・K4 も同じ形。`L4 = if(sum(H4:K4),sum(H4:K4),0)` が総合計 |
| 行の挿入 | **できる。** 8〜32行の内側に1行挿入すると、グリッドは34行に、保護範囲は8〜33行に伸びる。**実シートで確認済み**（挿入後に削除して原状復帰） |
| 委託元の手順書 | 「ルール」シートの「シート追加手順」は、保護範囲を **8〜37行**で設定せよと指示している。**実物は 8〜32行**で、指示と合っていない |

**手順書と実物が食い違っている。** シートの追加は委託元の担当者の手作業であり、
**指示どおりに設定されているとは限らない。**
N-11「行数を決め打ちにしない」の根拠は、これで一次資料になった。

**当初「実害のある落とし穴」として書いていた「合計式の範囲外に金額を書くと静かに漏れる」は、
起こらない。** 合計式の範囲が閉じていないため、シート内のどの行に書いても集計される。

**この誤りの出どころは xlsx への変換だった。** Excel は `H8:H` のような開いた範囲を表現できないため、
ダウンロード時にグリッドの下端で閉じた `H8:H33` へ置き換えられていた。
**ファイルから読める形と、実物の形が違っていた。**

代わりに、実装で気をつけるのは次の2点になる。

- **25行を超えるときは、書き込む前に行を挿入すること。** グリッドの外へは書けない
- **行数はスタッフごとに違う。** 自分のシートは25行だが固定値ではない。
  実行時に保護範囲とグリッドサイズを読んで判断すること

### 5.4 月度サイクル

ブック内の「ルール」シートに、委託元側の運用が書かれている。

| 時期 | 起きること |
| --- | --- |
| 翌月3日 正午 | **申請期限。** 入力権限が締められる |
| 翌月3日 午後 | 委託元が当月分の Excel をダウンロードする |
| 翌月4〜7日 | **シート消去 → 月度変更 → 権限公開** |
| 翌月7日以降 | 各自が入力できるようになる |

あわせて次の注記がある。

- 期限を過ぎた場合は翌月度に申請する
- タクシー／高速／駐車場費用は**領収書の添付が必要**
- タクシーや自家用車は、**シフトからの事前依頼や不測の事態の場合のみ**使用可能

**ここから分かる重要なこと**

- **当月分は当月中ずっと入力できる。** 月初にまとめる必要は本来ない
- **シートは毎月消去される。** つまり提出シートに履歴は残らない。
  「アプリは前月分の作業場であって履歴の保管庫ではない」（N-05）は、
  本人の意図としてだけでなく、**提出先の仕様としても正しい**
- **月度の切替期間（翌月4〜7日）は、翌月第1週の稼働日と重なる。**
  2026年9月なら、切替が起きる 9/4〜9/7 のただ中に 9/5・9/6 の稼働日がある。
  依頼は前月末（8/31）に届いており、**この時点で翌月分の案件が既にアプリの中にいる**（2章）。
  月度の切り替わりを引き金に実績データを消す（R-18）とき、**この案件を巻き込んではならない**（N-20）
- **祝日を入れると、この重なりはさらに濃くなる。** 稼働日は土日だけではない（2章）。
  翌月7日が月曜の祝日なら、**切替期間の最終日がそのまま稼働日**になる

### 5.5 API から読み書きしたときの挙動

**提出シートへ API から読み書きできることは、実機で確認済み**（2026-08-29）。
自分のシートの本文行に書き、読み戻し、消して元に戻せた。以下はそのとき分かった挙動。

| 確かめたこと | 結果 |
| --- | --- |
| 読み取り | できる |
| 本文行（8〜32行）への書き込みと削除 | できる |
| 保護範囲（1〜7行）への書き込み | **拒否される。** `400 INVALID_ARGUMENT`「保護されているセルやオブジェクトを編集しようとしています」 |
| 他人のシートへの書き込み | 保護範囲の `requestingUserCanEdit` が偽を返す。5.2 の例外2枚を除く |
| 日付の書き方 | `USER_ENTERED` で `2026/8/29` と書けば、文字列でなく**日付として入る**（シリアル値になる） |
| **入力規則** | **API 経由では一切効かない**（下記） |
| グリッド外への書き込み | `400 Range ... exceeds grid limits. Max rows: 33` |
| 行の挿入 | できる。保護範囲も一緒に伸びる |
| 結合セル（M8:M32） | 左上の M8 にも内側の M9 にも書けるが、**M9 の値は表示されない。** 見えないまま値だけが残る |
| 複数行の一括書き込み | できる。乗り換えありの案件を2行へ展開して書き、合計も正しく反映された。**ただし試した書き方は実際の記入と違う**（5.2「記入の実際」） |
| 改行を含む文字列 | 書ける。読み戻しても改行はそのまま保持される。領収書欄に複数の URL を並べられる |

**入力規則が効かないことの意味は重い。**
画面では弾かれる値が、API からはそのまま入ってしまう。次のすべてが素通りした。

- 存在しない会場コード（B列・`ONE_OF_RANGE`）
- 存在しない目的（C列・`ONE_OF_LIST`）
- 「往復／片道」以外の文字列（G列・`ONE_OF_LIST`）
- 負の金額 `-500`（H列・`NUMBER_BETWEEN` かつ `strict=true`）
- 数値欄への文字列（I列・`NUMBER_BETWEEN` かつ `strict=true`）

**`strict=true` が設定されている欄でも防げない。値の妥当性はアプリが担保するしかない。**

### 5.6 月度は API から読める

提出シートが今どの月を対象にしているかは、**自分のシートの A1 から機械的に取れる**（API 実測）。

| | 値 |
| --- | --- |
| 自分のシートの `A1` | `='交通費一覧'!A1` という数式。表示は `2026年8月` |
| `A1` の生の値 | **日付のシリアル値**（`2026年8月` なら `46235` = 2026-08-01） |
| 値の正本 | `'ルール'!C3` |

`valueRenderOption=UNFORMATTED_VALUE` で読めば、月度が数値として得られる。

**これで月度の切り替わりを検知できる。** 前に読んだ値と違っていれば、シートが消去されて
次の月度に入ったということ（5.4 の翌月4〜7日にあたる）。R-18 の自動削除は、これを引き金にできる。

## 6. 依頼メールの仕様

**Gmail API で実物を直接読んで確かめた**内容（2026-08-31 実施、`tools/gmail-probe/`）。
独自ドメインに届いた **案件詳細メール1通と依頼無しメール1通**が対象。

> **サンプルは各1通しかない。** 「常にそうなる」と言い切れるのは、書式が委託元の
> システムから機械生成されている見込みが高いことを根拠にした**推定**である。
> 実測できたことと、そこからの推定を分けて書く。

委託元専用の Gmail ラベルに、**2種類のメールが届く。件名で機械的に判別できる**（API 実測）。

| | 案件詳細メール | 依頼無しメール |
| --- | --- | --- |
| 件名 | `<YYYY/MM/DD>案件詳細です。` | `【<M>月<D>日(曜) 依頼無しのご連絡】` |
| 中身 | 1件の撮影案件の詳細 | その日は依頼が無いという連絡 |
| 扱い | **案件として取り込む** | **取り込まない** |

**件名は文書に書いた書式と厳密に一致した**（API 実測）。どちらも正規表現で判別できる。

**依頼無しメールの件名には年が入らない**（API 実測）。本文にも日付が無く、
「スタッフ各位」で始まる定型文だけ。**件名の `M月D日(曜)` は取れるので、
取れないのは年だけである。** 取り込まない種別なので支障はない。

### 6.1 ラベルではなく差出人で判別する

**ラベルを付けているのは委託元ではなく、自分の Gmail フィルタである。**
独自ドメインへ切り替わった直後、フィルタを作っていなかったため、
**最初の2通はラベルが付かないまま届いた**（2 参照）。

| 引き方 | 結果（API 実測） |
| --- | --- |
| ラベルIDで引く | 2通 |
| `from:<差出人>` で引く | 2通。**ラベルと同じ集合** |

差出人アドレスは**2種類のメールで同一**（表示名だけ違う）。したがって
**差出人だけでラベルと同じ集合が取れる**（API 実測）。

**宛先では判別できない**（API 実測）。`To` には自分以外の宛先も入っており、
**依頼無しメールでは自分が `To` に居ない**（Bcc で届いている）。
`Delivered-To` はどちらも自分のアドレス。

転送は挟まっていない（`X-Forwarded-*` ヘッダ無し・API 実測）。委託元から直接届いている。

### 6.2 メールの構造

| 確かめたこと | 結果（API 実測） |
| --- | --- |
| 最上位の MIME 型 | `multipart/alternative` |
| パート構成 | `text/plain` と `text/html` の2つ。**どちらも本文データを持つ** |
| 文字コード | **どちらも UTF-8。** ISO-2022-JP ではない |
| 添付ファイル | 無し |
| 大きさ | 案件詳細は約 75KB（平文 3,584字／HTML 55,935字）、依頼無しは約 8KB |
| 取れる鍵 | `id` / `threadId` / `internalDate` / `historyId`。プロフィールからも `historyId` が取れる |

**平文と HTML は同じ内容を持つが、落ちるものが違う**（API 実測）。片方だけでは足りない。

| | 残るもの | 落ちるもの |
| --- | --- | --- |
| `text/plain` | 各リンクの URL が本文に並ぶ | 表のセル境界。**スタッフ2名が空白区切りの4語に潰れる** |
| `text/html` | `td` の境界（タブとして取り出せる） | `href`（本文テキストに現れない） |

**HTML には目印が無い。** `class` も `id` も、Gmail が挿入した `gmail-in-cell-link` 以外に
存在しない。したがって**どちらのパートを読むにせよ、見出しと位置で読むことになる。**

### 6.3 案件詳細メールから取り出せるもの

**次のすべてを実際に取り出せた**（API 実測）。

| 項目 | 取り出し方 |
| --- | --- |
| 施行日 | `施行日` 行から。`YYYY/MM/DD` |
| 会場名 | 先頭ブロックの2行目 |
| **会場コード** | 先頭ブロックの3行目。3文字前後の英数字 |
| ご両家名 | 先頭ブロックの4行目。`〇〇様 △△様` |
| 挙式・披露宴の開始時刻と場所 | `挙式` `披露宴` 行から |
| **案件番号** | `案件番号 : <数字9桁>` |
| 撮影アイテムとスタッフの割当 | 「アイテム／スタッフ1…」の表から。**HTML 側でないと担当者を切り分けられない** |
| 当日の緊急連絡先 | `▶<氏名> <電話番号>` |
| 各種リンク | 8本（案件承諾・出発報告・終了報告(撮編)・終了報告(音響)・案件資料・ポータル・不具合報告・緊急連絡網） |

**先頭の4行には見出しが無く、位置で読むしかない。** ただし裏は取れる。
**1行目の日付が「施行日」行の日付と一致し、4行目が `〇〇様 △△様` の形である**ことを
確かめてから、2行目を会場名・3行目を会場コードとして採る。
書式が変われば裏取りが失敗するので、**黙って別の値を拾うのではなく「取れなかった」と分かる**（N-16）。

**リンクは委託元のメール配信サービス（YAMM）の計測用 URL になっている**（API 実測）。
本文末尾には開封計測用のビーコン画像も入っている。
「案件承諾」は今回扱わない（9 参照）が、**リンクを叩くと計測される**ことは変わらない。

### 6.4 メールと提出シートが直結している

ご両家名の書式はシートの記入例と一致する。したがって次の対応が機械的に付く。

```
依頼メール              提出シート
--------------------    --------------------------
施行日              →   A列  日付
会場コード          →   B列  目的地(会場)
（婚礼案件で固定）  →   C列  目的
ご両家名            →   D列  案件名(新郎/新婦)
```

**人が入力するのは E〜I 列（出発駅・到着駅・往復/片道・金額・タクシー）だけ**になる。
案件番号は、同じ案件を二重に取り込まないための鍵として使える。

**ただし会場コードは、そのまま書けない**（下記）。

### 6.5 会場コードがマスタに無いことが実際に起きた

ヒアリングでは「会場コードは依頼メールと提出シートで**常に一致する**」と確認していた。
**この前提は、最初の実測で崩れた**（API 実測）。

| 調べたこと | 結果 |
| --- | --- |
| B列の入力規則が参照している範囲 | `'会場'!$A:$A`（`ONE_OF_RANGE`） |
| 会場マスタ | 43件。コードと会場名の2列 |
| 依頼メールの会場コード | **マスタに存在しない** |
| 前後空白・大小文字を無視した照合 | それでも一致しない。**表記ゆれではない** |
| 会場名での照合 | **マスタに載っていない。会場そのものが未登録** |

**この1件だけでは原因を断定できない。** 新しい会場が増えてマスタの更新が遅れているのか、
別の理由があるのかは分からない。**分かったのは「起こる」ということ**である。

**N-14 は用心のための想定ではなく、実際に起きる。** 入力規則は API 経由では効かない（5.5）ため、
存在しないコードもそのまま書き込めてしまう。**書く前に照合する**必要がある。

**そのうえで、そのコードはそのまま書かれて提出されていた**（2026-08-31 実測）。
本人は提出シートの B列に、マスタに無いコードを手で入力している。
B列の入力規則は `strict` ではないため、**画面でも警告が出るだけで値は入る。**
会場マスタは同日に読み直したが、43件のままでそのコードは今も無い。

**ここで方針が決まった。** 照合して知らせることは要るが、**書き込みを止めてはいけない。**
止めれば、人が手でできることをアプリだけができなくなる。N-14 をそう改めた。

### 6.6 依頼メールが届く時期

**2通とも、施行日と同じ週の月曜に届いていた**（API 実測）。
2章に書いた到着タイミングは、これで1週ぶんの裏が取れている。

| | 案件詳細メール | 依頼無しメール |
| --- | --- | --- |
| `Date` ヘッダ | `Sun, 30 Aug 2026 22:43:11 -0500` | `Mon, 31 Aug 2026 12:49:15 +0900` |
| **JST 換算** | **2026-08-31（月）12:43** | **2026-08-31（月）12:49** |
| 対象の日 | **2026/09/06（日）**（施行日） | **9月5日(土)**（件名） |
| 対象日までの日数 | **6日** | **5日** |

**案件詳細メールのタイムゾーンが `-0500` なのは、委託元の配信サービス側の時刻だからである**
（6.3 の YAMM）。JST に直せば、2通とも**同じ月曜の昼12時台**に届いている。

**この2通は、その週の稼働日を覆っている。** 9/5（土）は「依頼無し」、9/6（日）は案件あり。
**依頼の有無にかかわらず、週の頭にその週の稼働日ぶんがまとめて届く**という形が見える。

**そして、月をまたいでいる。** 8月に受信し、9月に施行する。
**月初の案件が前月末に取り込まれる**（2章・N-20 / N-21）ことが、実データで確かめられた。

> **サンプルは1週ぶんしかない。** 「毎週かならずこの形になる」と言えるのは本人談のほうで、
> 実測が示すのは **この週はそうだった**ことである。両者は食い違っていない。
>
> **しかも、この週に祝日は無い。** 9/7（月）は平日である。
> **月曜祝日の3連休が同じ回にまとまること（2章）は、実測できていない**（10章）。

## 7. アプリで実現したいこと（To-Be）

### シーン① 依頼が来たとき

Gmail に届いた依頼メールから、案件が **自動でアプリに入っている**。自分では何もしない。
依頼無しの連絡は取り込まれない。拾えなかった案件や取り違えだけ、後から手で直す。

### シーン② 現場からの帰り道

その日に使った経路が確定した時点で、**移動中のスマートフォンから、その場で記録を終える**。
案件を選び、登録済みのルートから実際に使ったものを選ぶだけでよい。
タクシーを使った日は、金額を入れて領収書をアップロードすれば、ドライブへの保管まで終わっている。

### シーン③ 提出するとき

前月分がすでに揃っているので、内容を確認して **書き込むだけ**。
提出シートに反映されたら、その月分の作業は完了する。以降そのデータを見ることはない。

提出シートは当月分を当月中ずっと受け付ける作りなので、
記録がその日のうちに済んでいれば、**月初にまとめて思い出す作業そのものが消える。**

- **必須** — これが無いと「4. 現状の課題」が解けない
- **望ましい** — あるとよいが、無くても運用は回る

### 8.1 案件管理

### 8.4 領収書

| ID | 要求 | なぜ要るのか | 優先度 |
| --- | --- | --- | --- |
| R-11 | タクシーを使った日は、金額と領収書を記録したい | 提出シートでタクシー費用には領収書添付が必須とされているため | 必須 |
| R-12 | 領収書はタクシー乗車1回につき1件。その1件をアップロードできるようにしたい | 乗車と領収書は常に1対1で対応する | 必須 |
| R-13 | 領収書の実体は、紙を撮影した画像のことも PDF のこともある。どちらの形式でも受け付けたい | 紙の領収書をもらう場合と、配車アプリから PDF を落とす場合の両方があるため | 必須 |
| R-14 | アップロードした領収書が Google ドライブへ自動で保存されるようにしたい | 現状は自分でドライブへ置いている（課題6）。ここを無くす | 必須 |
| R-21 | **保存した領収書を、委託元が開ける状態に共有してほしい** | Drive の既定は非公開。ここが抜けると **URL は書けているのに担当者が開けない**という形で静かに失敗する。現行運用は「リンクを知っている全員が閲覧可」で、**その共有はファイル単位で付いている**（3 参照・N-19） | 必須 |

> **領収書欄は月に1枠しかない**（M8:M32 は単一の結合セル・5.2 参照）。
> したがって R-15 は「乗車ごとに1セル」ではなく、**その月の URL を改行で区切って
> 1つのセルに並べる**形になる。委託元の担当者が文字列として読めればよいと確認済み。
> R-12 の「乗車1回につき1件」はアプリ側での領収書の持ち方の話であり、この書き方と両立する。

> **1日に複数回タクシーへ乗ることがある。** 実例では往路と復路で2回乗り、領収書も2件あったが、
> **提出シートの I列にはその日の合計額を1つだけ書いている**（本人確認済み・5.2）。
> したがって提出時は、**金額は日ごとに合算し、URL は乗車ごとに並べる**ことになる。

### 8.5 提出

| ID | 要求 | なぜ要るのか | 優先度 |
| --- | --- | --- | --- |
| R-16 | 前月分をまとめて提出シートへ書き込めるようにしたい | 手入力（課題1）そのものを無くすのが、このアプリの目的 | 必須 |
| R-17 | 提出前に内容を確認できるようにしたい | 提出先は委託元の所有物であり、誤った内容をそのまま書き込むわけにいかない | 必須 |
| R-18 | 提出が済んだ月の実績データを、**次の月度が始まった時点で自動的に消してほしい** | 提出後にそのデータを活用する意図が無いため（N-05）。**提出シートの月度は API から読める**ので、切り替わりを検知して消せる（5.6 参照） | 必須 |
| R-22 | **月初に、提出をうながすメールを受け取りたい** | 締切は翌月3日正午（2 参照）で、過ぎた分はアプリで面倒を見ない（9章）。**アプリを開かなければ、未提出であることに気づけない。** 気づく手立てを1つ持ちたい | 望ましい |

> **R-22 は、このアプリが新しく作るリスクへの対処である。**
> 現状は「月初にまとめて手入力する」という作業そのもの（3章の手順5）が、提出を思い出す引き金に
> なっている。**アプリを入れると、その作業が消える**（7章・シーン③）。記録は稼働日の帰り道に
> 済んでおり、**月初にアプリを開く動機が無くなる。** 開かなくても届く経路が要るのはそのためである。
>
> **優先度を「望ましい」としたのは、無くても運用が回るからである。**
> 提出忘れは4章の課題に挙がっておらず、**見たうえで忘れたなら手で書く**（9章）という整理も変わらない。
> アラートは**気づく手立て**であって、提出を保証するものではない。

> **削除を「提出した瞬間」にしないのには理由がある。**
> 委託元から差し戻しや修正依頼が**まれに来る**と確認した。提出（翌月3日正午まで）から
> 月度切替（翌月4〜7日）までのあいだはデータが残っているので、その窓の中なら直せる。
> 切替後に差し戻しが来た場合は、提出シート側の運用（期限を過ぎた分は翌月度に申請・5.4）に従う。
>
> **消してよいのは「提出が済んだ月度」だけである。**
> 切替の時点で、アプリの中には**翌月第1週の案件も既に入っている**（N-20 / N-21）。
> これはまだ提出時期が来ていないだけで、消してよいものではない。
> **切替期間（翌月4〜7日）はその案件の稼働日と重なる**ため、ここを取り違えると
> 記録しようとしたその日に案件が消えている、という壊れ方をする。

### 8.6 非機能・制約

| ID | 制約 | なぜそうなるのか |
| --- | --- | --- |
| N-01 | 主な利用環境はスマートフォン（移動中・屋外）。PC 前提の操作量にしない | 入力する場所が現場への道中と帰り道だから |
| N-02 | Google Workspace（Gmail / Google ドライブ / Google スプレッドシート）が前提環境 | 依頼受信・領収書保管・提出のすべてがこの上で回っている |
| N-03 | 利用者は本人のみ | 自分専用として使う。共有・権限分離の要求は無い |
| N-04 | 提出シートは委託元の所有物。壊さないこと、様式変更に追従できることが要る | 自分の資産ではないため、書き込みで既存の内容を損なってはならない |
| N-05 | **アプリが扱うのは「提出前の前月分」だけ。** 提出後の記録の正本は提出シートと Google ドライブ（領収書）にあり、アプリは正本ではない | アプリの目的は「前月分を入力し終えること」であり、記録の保管庫ではない |
| N-06 | ただし **ルートの登録内容と会場との紐付けは、毎月使い回す設定データとして残り続ける** | ここが消えると「登録済みルートを選ぶだけで済む」（R-05〜R-07）が成立しない |
| N-07 | 提出シートの保護範囲・入力規則・合計式に手を触れないこと | 委託元の所有物であり、保護範囲へ書こうとすれば拒否される（5.5 参照） |
| N-08 | スプレッドシートID・シート名・フォルダID・会場コードの実値などの環境依存値は、リポジトリに含めず `.env` で管理する | このリポジトリは public であり、委託元と他スタッフの情報を含むため |
| N-09 | **書き込む値の妥当性は、アプリ側で検証すること。** 会場コード・目的・往復/片道・金額のいずれも | **入力規則は API 経由では効かない。** 画面で弾かれる値も素通りして入り、誤ったまま提出される（5.5 参照） |
| N-10 | **書き込む前に、行が足りているかを確かめること。** 足りなければ行を挿入する | グリッドの外へは書けない。自分のシートは 8〜32行の25行しかなく、1案件が複数行になるため足りなくなり得る（5.3 参照） |
| N-11 | **行数・保護範囲は実行時に読んで判断すること。** 25行という値を決め打ちにしない | 行数はスタッフごとに違い、行の挿入でも変わる（5.3 参照） |
| N-12 | **他人のシートへは、いかなる場合も書き込まないこと** | 委託元側の保護設定の不備で、他スタッフのシートを2枚編集できてしまう状態にある（5.2 参照） |
| N-13 | **提出シートへのアクセスは、委託元が管理する「リンク共有」の上に載っている。** 委託元が共有設定を締めた時点で、アプリはシートを読み書きできなくなる | 独自ドメインのアカウントは個別に招待されておらず、`anyone` の編集権だけでアクセスできている（5.1 参照）。自分では制御できない前提であり、失われたときに気づける必要がある |
| N-14 | **会場コードは、書き込む前に提出シートの会場マスタと突き合わせること。** 見つからなければ**知らせる。ただし書き込みは止めない** | **想定ではなく実際に起きた**（6.5）。しかも**本人はそのコードをそのまま書いて提出している**。B列の入力規則は `strict` ではなく、画面でも警告が出るだけで値は入る。**止めれば、人が手でできることをアプリだけができなくなる。** 知らせる相手は本人であって、委託元ではない |
| N-15 | **依頼メールの判別は、ラベルではなく差出人アドレスを一次条件にすること** | ラベルを付けているのは委託元ではなく**自分の Gmail フィルタ**で、フィルタが無い状態で依頼メールが届いた実例がある（2 参照）。ラベルだけに頼ると、**取り込みは例外を出さずに静かに止まる。** 差出人だけでラベルと同じ集合が取れると実測済み（6.1） |
| N-16 | **メールから位置で読む項目は、裏を取ってから採ること。** 裏取りに失敗したら、値を拾わずに「取れなかった」として知らせる | 案件詳細メールの会場名・会場コード・ご両家名には見出しが無く、先頭からの位置で読むしかない（6.3）。書式が変わったとき、**黙って別の値を拾って提出してしまうのが最悪の壊れ方**である |
| N-17 | **宛先（`To`）で依頼メールを判別しないこと** | 依頼無しメールは**自分が `To` に居ない**（Bcc で届く）。`To` には他スタッフのアドレスも入る（6.1） |
| N-18 | **ラベル名と差出人アドレスも `.env` で管理する** | どちらも委託元が特定できる値であり、N-08 と同じ理由でリポジトリに含められない |
| N-19 | **領収書は、アップロードしたファイルごとに共有権限を付けること** | 現行運用を実測したところ、**フォルダは非共有のままで、各ファイルに個別の共有（`anyone / reader`）が付いていた**（3 参照）。フォルダ側に付けて継承させる手もあるが、**現に回っているのはファイル単位のほう**である。何も付けなければ非公開のままで、**URL は書けているのに担当者が開けない**という形で静かに失敗する（R-21） |
| N-20 | **案件が属する月度は、施行日で判定すること。取り込んだ日で判定しない** | 依頼は月曜に届き、覆う範囲はその週の稼働日と連なる月曜の祝日までなので、**月初の案件は前月末に取り込まれる**（2章）。取り込み日で判定すると、翌月の案件が前月度のものとして扱われ、**月度の切り替わり（R-18）で消える。** しかも取り込み済みメールは再取り込みを防ぐために残すので、**消えた案件は戻ってこない。** 切替期間（翌月4〜7日）は**翌月第1週の稼働日と重なる**ため、これは想定ではなく毎月ここで起きる |
| N-21 | **アプリは常に2か月分の実績データを同時に保持できること** | 月末の最終月曜から翌月分が入り始め、月初は前月分（提出待ち）と当月分が並走する（2章・5.4）。**N-05「扱うのは提出前の前月分だけ」は保持期間の話であって、同時に1か月分しか持てないという意味ではない。** ただし先の月度として持つのは**翌月第1週分だけ**で、それより先は届かない |
| N-22 | **アプリは祝日を判定しない。祝日カレンダーを持たない** | 稼働日には祝日が含まれる（2章）が、**施行日は依頼メールから来る値**であり、アプリがカレンダーから稼働日を導く箇所は1つも無い。持てば、毎年の改正に追従する責任だけが増える |
| N-23 | **アプリが送るメールの宛先は、本人のアドレス固定とする。実行時に決めない** | R-22 で、このアプリは初めて**メールを送る側**になる。**委託元や他スタッフへ誤って送る経路を、そもそも作らない。** N-12（他人のシートへ書かない）と同じ考え方である |

> **N-05 と N-06 の区別は重要。**
> 消えてよいのは **月次の実績データ**（案件・交通費・領収書）。
> 残り続けるのは **設定データ**（ルート、会場とルートの紐付け）。
>
> **そのうえで、N-20 が「どの月の実績か」を決める。**
> 消してよいかどうかは月度で決まり、その月度は**施行日**から決まる。

## 11. 用語集

| 用語 | 意味 |
| --- | --- |
| 委託元 | 撮影業務を発注してくる企業。現在1社 |
| 案件 | 1件の撮影業務。施行日・会場・ご両家名で識別される |
| 案件番号 | 依頼メールに載っている案件の識別番号。二重取り込みを防ぐ鍵に使える |
| 受注 | 届いた依頼を受けることを決め、案件として確定させること |
| 稼働日 | 撮影のために現場へ出る日。**主に土日と祝日**（2章）。アプリはこの日をカレンダーから導かず、**依頼メールの施行日をそのまま使う**（N-22） |
| 会場 | 撮影する結婚式場 |
| 会場コード | 会場を表す3文字前後の英数字コード。依頼メールと提出シートの双方で使われる |
| ご両家名 | 結婚する二人の両家の姓。提出シートには `〇〇様△△様` の形式で書く |
| ルート | 自宅と会場の間の行き方。複数の区間と運賃の組み合わせ |
| 区間 | 出発駅と到着駅の1組。**提出シートの1行がこれにあたる** |
| 往路／復路 | 会場へ向かう行き／会場から帰る行き。別々のルートになることがある |
| 提出シート | 委託元が用意した Google スプレッドシート。交通費の提出先 |
| 社員番号 | 委託元が各スタッフに割り振る番号。提出シートのシート名に含まれる |
| 月度 | **提出シートが対象としている月。** 毎月、締切後にシートが消去されて次の月度に切り替わる。値は自分のシートの `A1` から読める（5.6） |
| 案件の月度 | **その案件の施行日が属する月**（N-20）。取り込んだ日ではない。月初の案件は前月末に取り込まれるため、この2つは毎月ずれる（2章） |
| 対象月度 | **これから提出シートへ書き出す月度。** 提出シートの `A1` が示す月を正とする |
| 実績データ | ある月に実際に発生した案件・交通費・領収書。提出後は残す必要がない（N-05）。**どの月のものかは案件の月度で決まる**（N-20） |
| 設定データ | ルートの登録内容と、会場とルートの紐付け。毎月使い回す（N-06） |
