# 交通費精算アプリ 要件定義

## 1. この文書について

この文書は、交通費精算アプリが **何を満たさなければならないか** を決めたものである。
要求分析（[`docs/requirements-analysis.md`](requirements-analysis.md)）の次に置く。

- **扱うこと** — システム構成の形、機能要件、提出シートへの書き出し仕様、論理データモデル、
  外部連携の仕様、画面の役割、非機能要件、異常系
- **扱わないこと** — **技術選定（言語・フレームワーク・データベース製品）**、画面の見た目、
  物理データモデル、インフラ構成。これらは設計以降で決める
- **出どころ** — 要求分析と、そこから決まらなかった論点についての依頼者本人への確認（2026-08-31）

> **このリポジトリは public である。**
> スプレッドシートID・シート名・フォルダID・会場コードの実値・氏名・メールアドレスは
> **この文書に書かない**（N-08 / N-18）。例示はすべて架空の値を使う。

### 要求分析との関係

要求分析が「**なぜ作るのか・何が欲しいのか**」なら、この文書は「**それをどう満たすか**」である。
要求（`R-xx`）と制約（`N-xx`）は要求分析の番号をそのまま引き、
この文書では機能要件に `F-xx` を振る。対応は 12章に一覧で置く。

**要求分析だけでは決まらなかった論点が11件あった。** どれも「実績が無いので実測からは決まらない」
たぐいのもので、本人に確認して決めた。決定は次のとおり。**この11件が、この文書の骨格になっている。**

### 追加で決めたこと（2026-09-01）

**この文書を読み返す中で、依頼メールの到着タイミングが要求分析に無いことが分かった。**
本人に確認したところ、**依頼は施行日と同じ週の月曜以降にしか届かない**（要求分析 2章）。
つまり **月初の案件は前月末に取り込まれ、毎月かならず月をまたいで案件を持つ期間が生まれる。**

**これは実測でも確かめられている**（要求分析 6章）。2026-08-31（月）の昼に、
**その週の土日ぶん（9/5・9/6）が2通とも届いていた。** 8月に受信し、9月に施行している。
**ただし、この週に祝日は無い。** 祝日を含む週の配信は未実測である（決定16）。

上の11件は、この事実を知らないまま決めている。**月度の扱いだけが決め直しになった。**

> **この節の「施行日と同じ週の月曜以降にしか届かない」は、のちに撤回している。**
> 祝日を考慮に入れた時点で成り立たなくなった。**現行の規則は決定16** を見ること。

| # | 論点 | 決定 | 反映先 |
| --- | --- | --- | --- |
| 12 | **案件が属する月度** | **施行日で決まる。取り込んだ日ではない** | F-32 / 6.2 / 6.4 |
| 13 | **提出の対象月度** | **提出シートの `A1` が示す月を正とする。** カレンダーの前月ではない | F-31 / 5.2 手順1 |
| 14 | **月度切替後に前月分を翌月度シートへ申請する運用** | **アプリの対象外。手で入力する** | 5.5 / 10章 / 11章 |

**決定12 を落とすとデータが消える。** 取り込んだ日で月度を判定すると、8/31 に取り込んだ
9/5 の案件が8月度のものとして扱われ、**月度切替（翌月4〜7日）で消える。**
しかも切替期間は **その案件の稼働日そのもの**であり、取り込み済みメールが残るため
再取り込みもされない（6.3）。**記録しようとしたその日に、案件が消えている。**

**決定13 は要求分析 5.4 の実測とも合う。**「当月分は当月中ずっと入力できる」のだから、
提出はカレンダーの月初に縛られない。`A1` を正にすれば、**月度切替の前でも後でも、
月中の随時提出でも、判断が1つに定まる。**

### 追加で決めたこと（2026-09-04）

**設計（`architecture.md` / `screens.md`）まで進んだところで、本人から2件の申し出があった。**
**撮影は土日だけでなく祝日にも発生する**こと、
**月初に提出をうながすメール通知が欲しい**ことである。

| # | 論点 | 決定 | 反映先 |
| --- | --- | --- | --- |
| 15 | **祝日の稼働** | **稼働日は土日と祝日。ただしアプリは祝日を判定せず、祝日カレンダーも持たない** | 3章 / N-22 |
| 16 | **月曜祝日の依頼配信** | **土日に連なる月曜祝日の施行分は、前の週の月曜に届く。**「前の週には届かない」を撤回する | 9.2 / 要求分析 2章 |
| 17 | **提出アラート** | **バックエンドが定期実行でメールを送る。** Gmail API の送信スコープを使い、**1日と3日の朝、対象月度が未提出のときだけ** | F-35 / F-36 / NF-04 / NF-13 / 7.5 |

#### 決定15・16 で、機能要件は1つも変わらない

**これは確かめた結果であって、確かめずに済ませてよいことではない。**

| 変わらないもの | なぜ |
| --- | --- |
| **F-32 の削除条件** | 「切替先より前」かつ「提出が済んだ」月度だけを消す。**判定に曜日が出てこない** |
| **決定12（案件の月度は施行日で決まる）** | 施行日は依頼メールから来る値であり、祝日かどうかは関係しない |
| **9.2 の「常に2か月分」** | 配信が覆う最も遠い日は翌月7日までで、**3か月分が並ぶ経路は生まれない**（下記） |
| **5章の書き出し仕様すべて** | 提出シートは日付を受け取るだけで、**その日が何曜日かを見ていない** |

**アプリが祝日を判定する箇所は、1つも無い**（N-22）。施行日は依頼メールから取り出す値であり
（F-06）、手で足す場合も人が入れる（F-10）。**カレンダーから稼働日を導く経路が無いので、
稼働日に祝日が加わっても、判定するものが増えない。**

#### 決定16 は、前提を1つ壊している

「追加で決めたこと（2026-09-01）」で **「前の週には届かない」**と書いたが、
**祝日を入れた時点で成り立たなくなった。**
9/5（土）・9/6（日）・9/7（月）に撮影が入り 9/7 が祝日だったとすれば、
**3件とも 8/31（月）に届く**（要求分析 2章）。**猶予の上限は6日から7日になる。**

**それでも 9.2 の結論は動かない。** 配信は月曜 M で、覆う最も遠い日は M+7 である。
M が前月に属する最後の月曜なら **M は前月の末日から6日以内**にあり、
したがって **M+7 は翌月1日から7日のあいだ**にしかならない。月の日数によらずそうなる。
**「先の月度として持つのは翌月第1週分だけ」は、そのまま成り立つ。**

#### 決定17 は、11章で対象外としたものを覆している

11章は「提出期限のリマインド」を **要求に無い**・**決定1 と噛み合わない**という2つの理由で
外していた。**前者は消え、後者は残っている。** 何をどう折り合わせたかは 2.1 (3) と 11章に書く。

### さらに追加で決めたこと（2026-09-04・データベース設計の読み直しで）

**`database.md` を読み直す中で、複数のルートが同じ区間を持つケースが要件に無いことが分かった。**
本人に確認したところ、**最寄り駅が同じ会場が複数あり、自宅最寄り駅から先の区間は多くのルートで
共通する**（要求分析 8.2 / R-23）。

| # | 論点 | 決定 | 反映先 |
| --- | --- | --- | --- |
| 18 | **区間の持ち方** | **ルートから独立させ、複数のルートで共有する。運賃は区間が1つだけ持つ** | 6.1 / F-37 |

#### 決定18 が要るのは、直し漏れが静かに提出額を壊すからである

**区間をルートごとに持つと、同じ定義がルートの数だけ重複する。**
運賃改定でどれか1本を直し忘れると、**同じ区間なのに違う運賃を持つルートが残る。**
記録画面はルートの登録運賃をそのまま既定値にするので（`screens.md` 3.5）、
**エラーは出ず、違う額がそのまま提出される。**

**これは R-05 の動機を、設定データの側で作り直しているのと同じである。**
R-05 は「毎回ゼロから区間と運賃を書いている手間」を無くすためにあった（要求分析 8.2）。
**同じ区間を会場の数だけ書き直すなら、その手間は場所を変えて残っている。**

#### 決定18 は、6.1 の根拠を1つ壊している

6.1 は会場とルートを1対多にする理由を **「会場ごとに到着駅が違うため」**と書いていた。
**最寄り駅が同じ3会場では、到着駅は違わない。**
1対多を保つこと自体は変えないが、**根拠は差し替える**（6.1）。

### 「月」には3つの基準がある

**この文書で「月」と言うとき、次の3つが混ざりうる。混ぜると事故になるので、区別して書く。**

| 呼び方 | 何を指すか | どこから決まるか |
| --- | --- | --- |
| **当月・前月・翌月** | **カレンダー上の月。** 今日が何月か | 時計 |
| **対象月度** | **提出シートが今どの月を受け付けているか** | 自分のシートの `A1`（決定13） |
| **案件の月度** | **その案件の施行日が属する月** | 案件の施行日（決定12） |

**この3つがずれるのが、毎月1〜7日である。**
たとえば 2026年9月2日の時点では、カレンダーは9月、対象月度は8月（切替は9/4〜9/7）、
案件は8月分と9月分の両方がアプリの中にいる。**提出作業をするのは、まさにこの期間である。**

### 更新の仕方

設計や実装の途中で要件がひっくり返ったら、**なぜひっくり返ったかを添えて**ここへ書き戻す。
要求そのものが変わった場合は、要求分析のほうも直す。

## 2. システム構成

**フロントエンド・バックエンド・データベースの3層とする。**
技術選定はここでは決めないが、**層の分け方と、各層が何を担うかは決める。**

| 層 | 担うこと |
| --- | --- |
| フロントエンド | 画面の描画と操作。スマートフォンのブラウザから使う（N-01）。**外部 API を直接叩かない** |
| バックエンド | 業務ロジック、外部連携（Gmail / ドライブ / スプレッドシート）、**認可情報の保持** |
| データベース | 設定データ・実績データ・システムデータの保存（6章） |

### 2.1 層の境界に置くルール

**(1) Google API を叩くのはバックエンドだけ。認可情報をフロントへ渡さない。**

提出シートは委託元の所有物で、リンク共有が「編集可」で付いている（要求分析 5.1）。
**この認可情報が漏れれば、他スタッフのシートにも書ける状態になる。**
ブラウザに置けば漏れるので、バックエンドの外へ出さない。

**(2) フロントエンドは記録を持たない。**

オフライン入力に対応しない（決定7）ため、入力はその場でバックエンドへ送る。
**端末とサーバーで内容が食い違う状態を作らない。**

**(3) 業務ロジックの定期実行を持たない。提出アラートの送信だけが例外**（決定1 / 決定17）。

依頼メールの取り込みも、月度切り替わりの検知も、**アプリを開いたときに走る。**
外部で動き続けるバッチを持たないので、構成が1つ減り、
「知らないうちに何かが起きていた」という状態も生まれない。

代わりに **「開くまで案件は入ってこない」** ことは受け入れる。ただし
**間に合わせる期限は提出時ではなく、稼働日の帰り道である。**
交通費の記録は案件を選ぶところから始まるので（F-18）、
**案件が入っていなければ、その場で記録できない。**

**猶予は長くない。** 依頼は月曜にしか届かず（要求分析 2章）、稼働までは最長7日。
シフト変更によるイレギュラーでは当日まで詰まる。

**それでも決定1 で足りるのは、記録画面へ入る前に取り込みが走るからである。**
帰り道にアプリを開けば、その時点で取り込みが実行され、案件が現れる。
**「3手で終わる」（8.1）は案件が既に入っていることを前提にしている**ので、
取り込みは記録の操作より前に済んでいなければならない。

**提出アラート（F-35）だけは、この形では成り立たない。**
アラートの目的は **アプリを開かない人に届くこと**であり、
開いたときに走らせては、**それが要る場面でだけ走らない。**

**そこで、定期実行を1本だけ持つ。** 決定1 を捨てるのではなく、**境界を引き直す。**

| 定期実行するか | 何を | なぜ |
| --- | --- | --- |
| **しない** | 案件の取り込み、月度切り替わりの検知 | 使う直前に走れば足りる。開いたときに走らせるほうが、状態のずれが生まれない |
| **する（1日1回）** | **提出アラートの判定と送信** | **開かない人に届けることが目的**であり、開いたときでは間に合わない |

**この1本が持ってよいのは、送るか送らないかの判断と、送信だけである。**
取り込みも書き込みも削除もここではしない。**データを変えないので、
「知らないうちに何かが起きていた」は起きない。**

### 2.2 外部システム

| 相手 | 使い方 | 権限 |
| --- | --- | --- |
| Gmail | 依頼メールを読む。**提出アラートを自分あてに送る** | **読み取りと、送信**（決定17） |
| Google ドライブ | 領収書を保存し、共有を付ける | 読み書き |
| Google スプレッドシート | 提出シートを読み、自分のシートへ書く | 読み書き |

**提出シートと領収書フォルダは、アプリの資産ではない**（N-04 / N-05）。
アプリは正本ではなく、**提出前の作業場**である。

## 3. 利用者と利用シーン

**利用者は本人1人**（N-03）。権限の分離もアカウント管理も要らない。

| いつ | どこで | 何をするか | 機能 |
| --- | --- | --- | --- |
| 依頼が届いた後（**施行日と同じ週の月曜。月曜祝日の施行分なら前の週**） | どこでも | アプリを開くと案件が入っている | F-03〜F-08 |
| **稼働日の帰り道** | **移動中のスマートフォン** | 案件を選び、使ったルートを選ぶ。タクシーに乗った日は金額と領収書 | F-18〜F-26 |
| 翌月1〜3日 | スマートフォンでも PC でも | 内容を確認し、提出シートへ書き込む | F-27〜F-30 |

**中心にあるのは2行目である。** ここが数タップで終わることが、このアプリの成否を決める
（要求分析の課題2・課題3）。他の画面が多少手数を要しても、ここだけは短く保つ。

**1行目と3行目は、月をまたいで重なる。** 依頼は月曜に届くので
（要求分析 2章）、**翌月1〜3日に前月分を提出しているとき、当月第1週の案件はもう入っている。**
アプリは常にこの2つを同時に抱える（9.2）。

利用の規模は次のとおり。**小さい。**

| | 量 |
| --- | --- |
| 案件 | 月6〜10件 |
| 稼働日 | 主に土日と祝日 |
| 提出シートへ書く行 | 月20〜30行（5.3 の見積もり） |
| 領収書 | 月に数件 |

## 4. 機能要件

`F-xx` が機能要件の番号、「要求」列は要求分析の `R-xx` / `N-xx` に対応する。

### 4.1 認証とアクセス

| ID | 要件 | 要求 |
| --- | --- | --- |
| F-01 | **Google アカウントでログインする。許可されたアカウント以外は利用できない** | N-03 / 決定5 |
| F-02 | Google API の認可を保持する。**失効・喪失したら、その旨を知らせて再認可へ導く** | N-13 |

**F-02 は「静かに壊れる」経路を塞ぐためにある。**
提出シートへのアクセスは委託元が管理するリンク共有の上に載っており、
**委託元が共有を締めた時点で読み書きできなくなる**（N-13）。
これは自分では制御できない。**失われたときに気づけることだけが対策になる。**

### 4.2 案件の取り込み

| ID | 要件 | 要求 |
| --- | --- | --- |
| F-03 | **アプリを開いたときに依頼メールを取り込む。** 画面の操作でも実行できる | R-01 / 決定1 |
| F-04 | **差出人アドレスを一次条件に**依頼メールを集める。ラベルを条件にしない。宛先で判別しない | N-15 / N-17 |
| F-05 | 件名で種別を判別し、**「依頼無し」のメールは取り込まない** | R-19 |
| F-06 | 案件詳細メールから **施行日・会場コード・会場名・ご両家名・案件番号** を取り出す | R-03 |
| F-07 | **位置で読む項目は裏を取ってから採る。** 裏取りに失敗したら値を採らず、要確認事項として残す | N-16 |
| F-08 | **案件番号で二重取り込みを防ぐ。** 同じメールを何度取り込んでも案件は増えない | R-03 |

**F-04 の「ラベルを条件にしない」は、実際に起きた失敗が根拠である。**
ラベルを付けているのは委託元ではなく本人の Gmail フィルタで、
フィルタが無い状態で依頼メールが届いた実例がある（要求分析 6.1）。
**ラベルだけに頼ると、取り込みは例外を出さずに静かに止まる。**

**F-07 が守るのは「黙って別の値を拾わない」ことである。**
会場名・会場コード・ご両家名には見出しが無く、先頭からの位置で読むしかない（要求分析 6.3）。
書式が変わったとき、**間違った値を拾って提出してしまうのが最悪の壊れ方**であり、
「取れなかった」と分かるほうが良い。裏取りの具体は 7.2 に書く。

### 4.3 案件の管理

| ID | 要件 | 要求 |
| --- | --- | --- |
| F-09 | **提出待ちの月度と、それ以降の施行日を持つ案件**を**一覧で見られる**。記録が済んだかどうかが分かる | R-02 / 決定12 |
| F-10 | **案件を手で追加できる**（自動で拾えなかったとき） | R-04 |
| F-11 | 取り込んだ案件の項目を**手で直せる** | R-04 |

**F-09 の範囲を「当月と前月」で切らない**（決定12）。
月初の案件は前月末に取り込まれるため（要求分析 2章）、カレンダーの月で切ると
**8/31 に取り込んだ 9/5 の案件が、どこにも出てこない。**

**これは表示だけの問題ではない。** 10章は「差出人が変わると案件が入ってこなくなるだけで、
エラーは何も出ない」ことへの備えを、この一覧と「最後に取り込んだ日時」に賭けている。
範囲を月で切ると、**月末の取り込みではその備えが働かない。**

**F-12 は理由を区別しない。** 辞退・キャンセル・日程変更のいずれも起きるが、
アプリが判定する必要は無く、**消せることだけが要る**（R-20）。
削除すると、その案件に紐づく交通費記録・タクシー乗車・領収書のレコードも消える。
**ただしドライブ上のファイル実体は消さない**（6.4）。

### 4.8 月度の管理

| ID | 要件 | 要求 |
| --- | --- | --- |
| F-31 | **提出シートが今どの月を対象にしているかを読む。この値が対象月度になる** | 要求分析 5.6 / 決定13 |
| F-32 | **月度の切り替わりを検知したら、切り替わった先より前で、かつ提出が済んだ月度の実績データを自動で削除する** | R-18 / 決定10 / 決定12 |

**F-32 は確認を挟まない**（決定10）。検知したら黙って消す。
消えるのは実績データだけで、**設定データ（駅・区間・会場・ルート）は残る**（N-06）。

**消してよいのは、次の2つを両方満たす月度だけである。**

| 条件 | なぜ |
| --- | --- |
| **切り替わった先の月度より前であること** | **切替期間（翌月4〜7日）は、もう翌月第1週の稼働日と重なっている。** 依頼は月曜に届くので、9/4〜9/7 の切替の時点で 9/5・9/6 の案件は既にアプリの中にいる（要求分析 2章）。**翌月7日が月曜の祝日なら、切替の最終日がそのまま稼働日になる**（決定15） |
| **提出が済んでいること** | R-18 は「**提出が済んだ月の**実績データを」と言っている。提出記録の無い月度まで消すと、**入力したものが提出されないまま失われる** |

**どちらか一方でも欠けたら消さない。** ただし残し方は2通りに分かれる。

| 残るもの | 要確認事項に出すか |
| --- | --- |
| **提出していない、切替先より前の月度** | **出す**（F-33）。提出されないまま残っており、放置してよくない |
| **切替先以降の月度**（＝これから稼働する案件） | **出さない。** まだ提出時期が来ていないだけで、異常ではない |

**この区別を落とすと、毎月の切替でかならず誤検知が上がる。**
9/4〜9/7 の切替時、9月度に提出記録が無いのは当たり前である。
それを「未提出のまま切り替わった」と報せても、**本人にできることは何も無い。**

**案件がどの月度に属するかは、施行日で決まる**（決定12 / N-20）。取り込んだ日ではない。
取り込み日で判定すると、8/31 に取り込んだ 9/5 の案件が8月度のものとして扱われ、
**9/4〜9/7 の切替で消える。** しかも取り込み済みメールは再取り込みを防ぐために残すので
（6.3）、**消えた案件は戻ってこない。** 手で足し直す（F-10）しかなくなり、
それは屋外・移動中にキーボード入力を強いる（8.1 が避けようとしていること）。

削除を「提出した瞬間」ではなく「月度の切り替わり」にしているのは、
**差し戻しの窓を確保するため**である（要求分析 8.5）。
提出（翌月3日正午まで）から月度切替（翌月4〜7日）までのあいだはデータが残っている。

## 5. 提出シートへの書き出し仕様

**この文書でいちばん重要な章である。** 提出シートは委託元の所有物であり（N-04）、
壊してはならない。一方で提出シートの様式とアプリが扱う単位は食い違っており、
**その差を吸収するのがこのアプリの中心的な仕事**でもある。

シートの構造・保護範囲・入力規則・実際の記入のされ方は、
**要求分析 5章の実測がすべて前提になっている。**

### 5.1 原則

| # | 原則 | 根拠 |
| --- | --- | --- |
| 1 | **自分のシート以外には、いかなる場合も書き込まない** | N-12。他人のシートを2枚編集できてしまう状態にある |
| 2 | **保護範囲（1〜7行目）と合計欄（4行目の数式）には触れない** | N-07 |
| 3 | **行数・保護範囲は実行時に読んで判断する。25行を決め打ちにしない** | N-11 |
| 4 | **書き込む値の妥当性はアプリが担保する** | N-09。入力規則は API 経由では一切効かない |
| 5 | **一度の提出で、シートの状態は「アプリの内容と一致する」か「何も変わっていない」かのどちらか** | 5.5 |

**原則4を軽く見ない。** 画面では弾かれる値が API からは素通りする。
存在しない会場コード・存在しない目的・「往復／片道」以外の文字列・負の金額・
数値欄への文字列が、`strict=true` の欄でも**すべて入ってしまう**（要求分析 5.5）。
**シートは何も守ってくれない。**

### 5.2 実行手順

この順に実行する。**途中で条件を満たさなければ、何も書かずに中止する**（5.5）。

| # | すること | 根拠 |
| --- | --- | --- |
| 1 | **対象月度を決める。** 自分のシートの `A1` を `UNFORMATTED_VALUE` で読む。**この値が対象月度である** | 要求分析 5.6 / 決定13 |
| 2 | **構造を読む。** グリッドのサイズと保護範囲を読み、書き込める行の範囲を決める | N-11 |
| 3 | **様式を確かめる。** 7行目のヘッダーが想定どおりの並びかを見る | N-04 |
| 4 | **行を組み立てる。** **施行日が対象月度に属する案件だけを**、5.3 の規則で行に展開する | 決定12 / 決定13 |
| 5 | **行数を照らす。** 足りなければ、書き込める範囲の内側に行を挿入する | N-10 |
| 6 | **会場コードを照合する。** 「会場」シートと突き合わせ、無ければ**知らせる。止めない** | N-14 |
| 7 | **確認してもらう。** 組み立てた行と警告を、書き込む形のまま見せる | R-17 |
| 8 | **書き込む。** 本文行をクリアし、組み立てた行を書く | R-16 |

**手順1で対象月度をシートから読むのは、カレンダーの前月では決まらないからである**（決定13）。
翌月1〜3日ならカレンダーの前月と月度は一致するが、**月度切替（翌月4〜7日）を過ぎるとずれる。**
シートを正にすれば、**切替の前でも後でも、月中の随時提出でも、判断が1つに定まる。**

**手順4の絞り込みが無いと、翌月の案件が混ざる。**
9/1〜9/3 に8月分を提出するとき、アプリの中には 8/31 に取り込んだ 9/5・9/6 の案件がいる
（要求分析 2章）。絞らなければ **9月の日付が8月度のシートに書き込まれる。**
入力規則は API 経由では効かない（要求分析 5.5）ので、**A列に `2026/9/5` と書いても素通りする。**
5.1 原則4 の「値の妥当性はアプリが担保する」には、**どの案件を書くかの判断も含まれる。**

**手順3は、列の並びが変わったことに気づくためにある。**
提出シートは委託元の所有物であり、様式は変わりうる（N-04）。
**列の意味が変わったことに気づかずに書けば、別の欄へ値を書き込むことになる。**
金額の欄にご両家名が入るような壊れ方は、書いた側からは見えない。
ヘッダーが想定と違えば**中止する**（5.5）。

**手順5で行を挿入したら、それは要確認事項に残す**（F-33）。
シートの構造を変える操作であり、**委託元の資産に手を入れたことを本人が知っておくべき**だから。

**本文行を全部消してから書くのは、提出を何度でもやり直せるようにするためである**（決定2）。
どこまで書いたかをアプリが覚える必要が無く、**実行するたびにシートはアプリの内容と一致する。**
差し戻しが来ても、アプリ側を直してもう一度実行するだけでよい（F-29）。

**この方式は「本文行はすべてアプリが持つ」という約束の上に成り立つ**（決定11）。
**提出シートを手で直しても、次の提出で消える。**
直したいことがあれば、シートではなく**アプリ側を直してから提出する。**

**手順8のクリアと書き込みは、1回の一括更新にまとめる。**
別々に実行すると、クリアが通って書き込みが失敗したときに
**シートが空のまま残る。** 提出期限の直前にこれが起きると回復する時間が無い。

> 一括更新が「全部適用されるか、1つも適用されないか」になるのは API の仕様から言えることで、
> **実機では確かめていない。** 実装時に確認する（13章）。

### 5.3 行の生成規則

**対象にする案件** — **施行日が対象月度に属する案件だけ**（決定12 / 決定13）。
アプリの中には別の月度の案件も同時にいる（9.2）ので、**月度で絞ってから並べる。**

**並び順** — 施行日の昇順。同じ日に複数の案件があれば案件番号の昇順（決定4）。
**手で足した案件は案件番号を持たないことがある**（F-10）。その場合は登録した順に後ろへ置く。

**1案件が生む行** — 使ったルートの**区間の数だけ**行ができる。

| 往路と復路 | 行の作り方 | G列 | H列 |
| --- | --- | --- | --- |
| **同じルート** | 区間ごとに1行 | `往復` | その区間の**往復額** |
| **別のルート** | 往路の区間を並べ、続けて**復路のルートを反転**して並べる | `片道` | その区間の**片道運賃** |

**列ごとの規則**

| 列 | 書く内容 |
| --- | --- |
| A 日付 | 施行日。**案件の先頭行にだけ書く** |
| B 目的地(会場) | 会場コード。**先頭行にだけ書く** |
| C 目的 | **常に `婚礼案件`。先頭行にだけ書く** |
| D 案件名 | ご両家名。**先頭行にだけ書く** |
| E 出発駅 | 区間の出発駅。**全行に書く** |
| F 到着駅 | 区間の到着駅。**全行に書く** |
| G 往復 | `往復` または `片道`。**全行に書く** |
| H 金額 | その区間の運賃。**全行に書く** |
| I タクシー | **その案件のタクシー代の合計。先頭行にだけ書く** |
| J 高速代/駐車場 | **常に空** |
| K 車両 | **常に空** |
| L 備考 | **常に空** |
| M 領収書 | 5.4 のとおり。**月に1つの結合セル（`M8`）** |

**2行目以降の A〜D列を空にするのは、本人の実際の記入がそうなっているからである**（要求分析 5.2）。
**書けること自体は確認済みだが、書き方を実物に合わせる。**

**C列について、要求分析の記述は2つあり、一見食い違う。**
「乗り換え行は A〜D列を空にする」と「C列は全行『婚礼案件』」である（要求分析 5.2）。
前者が **`E〜H列だけを書く`** と具体的に述べているので、
**後者は「C列に値が入っている行は、どれも `婚礼案件` である」の意**と解釈した。
したがって **C列は案件の先頭行にだけ書き、2行目以降は空にする。**

**G列の `片道` は、実績の無い書き方である。**
実測では全行が `往復` だった（要求分析 5.2）。`片道` を書くのは往路と復路で
違うルートを使った日だけで（決定3）、**まだ一度も起きていない。**
最初にこれを書くときは、提出前の確認（F-27）で目視するのが望ましい。

**I列を「案件ごとの合計」にする理由。**
実測では「その日のタクシー代の合計」だったが、それは **1日1案件だったから**である。
稀に1日2件以上あり（決定4）、合計式は範囲が閉じていない `sum` なので
（要求分析 5.3）、**案件ごとに切り分けて書いても合計は正しくなる。**
日で寄せるより案件ごとのほうが、どの案件のタクシーかが分かる。

**運賃の持ち方。** 区間は**片道運賃**を持つ（6.1）。往復行では `×2` して書く。
実額とずれる場合は記録時に上書きする（F-20）。

**行数の見積もり** — 自分のシートの本文行は25行しかない（要求分析 5.3）。

| 案件数 | 1案件あたりの区間 | 行数 | 25行に収まるか |
| --- | --- | --- | --- |
| 10件 | 2（乗り換え1回） | 20行 | 収まる |
| 10件 | 3（乗り換え2回） | **30行** | **収まらない** |
| 8件 | 往路2＋復路2（別ルート） | **32行** | **収まらない** |

**行の挿入（手順5）は用心ではなく、実際に要る。**

### 5.4 領収書欄の書式

`M8:M32` は**丸ごと1つの結合セル**で、月に1枠しかない（要求分析 5.2）。
**対象月度の案件に紐づく領収書の URL** を、**日付の見出しを付けて改行で並べる。**
**本文行と同じ絞り込みを使う**（5.3）。書いた案件と URL の集合がずれると、
**行の無い領収書が並ぶ**ことになる。

```text
(9/5)
https://drive.google.com/file/d/<ファイルID>/view
https://drive.google.com/file/d/<ファイルID>/view
(9/12)
https://drive.google.com/file/d/<ファイルID>/view
```

| 規則 | 理由 |
| --- | --- |
| 日付の昇順に並べる | 担当者がタクシー代の行と突き合わせられる |
| **1行に URL は1本だけ** | M列は最終列で、はみ出した分の逃げ場が無い（幅577px、URL は約446px） |
| 書き込むのは結合セルの左上（`M8`）だけ | `M9` 以降にも書けてしまうが、**書いても表示されない**（要求分析 5.5） |
| 1日に複数回乗ったら URL を複数行並べる | 領収書は乗車ごとに1件（R-12）。**乗車の数と行の数は一致しない** |

### 5.5 中止する条件と、中止しない条件

**中止する**（何も書かない）

| 条件 | 理由 |
| --- | --- |
| **`A1` の月度を読めない・日付として解釈できない** | **対象月度が決まらない**（決定13）。どの案件を書くのかが定まらないまま書けば、他人ではなく自分の申請を壊す |
| 自分のシートが見つからない | 書く先が確定しない |
| **7行目のヘッダーが想定と違う** | 様式が変わっている。**別の欄へ書き込む事故を防ぐ**（N-04） |
| 提出シートを読めない・書けない（認可切れ・共有の停止） | N-13。**知らせて中止する** |
| 書き込める行の範囲を特定できない | 保護範囲が読めなければ、どこへ書いてよいか分からない |

**「シートの月度と対象月が違う」を中止条件から外したのは、決定13 の結果である。**
対象月度はシートの `A1` から決めるので、**そもそも食い違いようが無い。**
代わりに要るのは「`A1` を読めたか」の確認になった。

**月度が切り替わった後に前月分を出したくなった場合は、アプリでは扱わない**（決定14）。
提出シート側の運用（期限を過ぎた分は翌月度に申請・要求分析 5.4）に従い、**手で入力する。**
年に何度あるかの例外のために、**対象月度と施行日がずれる経路をアプリに作らない。**

**中止しない**（知らせたうえで続ける）

| 条件 | 扱い | 理由 |
| --- | --- | --- |
| **会場コードが会場マスタに無い** | **警告を出し、そのまま書く** | N-14。実際に起きており、**本人は手で同じことをしている。止めれば、人にできることがアプリにできなくなる** |
| 交通費の記録が無い案件がある | その案件を飛ばし、警告を出す | 未入力に気づく機会になる。書ける分は書いたほうがよい |

### 5.6 書き出しの例

> 日付だけは、月またぎの説明（1章・9.2）と揃えるため実在の稼働日に合わせてある。
> **行の中身は実データではない。**

**アプリ側の内容**

## 6. 論理データモデル

**何を持つか**を決める。テーブル定義・型・索引は設計で決める。

データは性質で3つに分かれ、**消えるものと残るものがはっきり違う**（N-05 / N-06）。

| 区分 | 中身 | 寿命 |
| --- | --- | --- |
| **設定データ** | 駅・会場・ルート・区間 | **残り続ける** |
| **実績データ** | 案件・交通費記録・タクシー乗車・領収書・提出記録 | **月度の切り替わりで消える。ただし消えるのは提出が済んだ過去の月度だけ**（6.4） |
| **システムデータ** | 取り込み済みメール・同期状態・要確認事項・認可情報 | 用途ごと（6.4） |

### 6.1 設定データ

| エンティティ | 主な属性 |
| --- | --- |
| **駅** | 名前（**鉄道会社の略称込み**） |
| **区間** | 出発駅・到着駅・**片道運賃**。**複数のルートで共有される**（決定18） |
| **会場** | 会場コード・会場名・出どころ（マスタ由来／自分で追加） |
| **ルート** | 名前・紐づく会場・**使う区間の並び** |

**関連**

```
会場 1 ──── * ルート * ──── * 区間 * ──── 1 駅（出発）
                                   * ──── 1 駅（到着）
```

**ルートと区間は多対多で、その間に順序がある。**
ルートは**登録済みの区間を並べたもの**であって、区間そのものを抱え込まない。

**ルートは「自宅→会場」の1方向で持つ**（決定9）。復路に使うときは、
**区間の並びを逆順にし、各区間の出発駅と到着駅を入れ替える。**
往復で経路が違う場合は、その経路を別のルートとして登録し、復路として選ぶ。

**区間はいくつでも並べられる。** 乗り換え無しなら1つ、1回なら2つ、2回なら3つ。**上限を設けない。**

**「駅を N 個並べて、その間を区間とみなす」形にはしない。**
乗換駅は鉄道会社ごとに別の駅として書かれるため（要求分析 5.2）、
**前の区間の到着駅と次の区間の出発駅は、乗り継ぐ同じ場所でも文字列として一致しない**（5.6 の例）。
駅を連ねる形にすると、この書き分けができなくなる。
**区間ごとに出発駅と到着駅を独立して持つ。**

**同じ区間は1つしか持たない**（決定18）。出発駅と到着駅の組が同じなら同じ区間であり、
**片道運賃はその区間が1つだけ持つ。**
最寄り駅が同じ会場が複数あるとき、「自宅最寄り駅→乗換駅」は多くのルートに現れる。
**ルートごとに運賃を持つと、運賃改定で直し漏れが起き、同じ区間なのに違う額が提出される。**

**実額とのずれは、設定データでは吸収しない。** その場で上書きする（F-20）。
**同じ駅ペアに運賃を2つ持たせると、どちらが正か決まらない。**

**会場とルートは1対多とする。** どの会場にどのルートを使うかは本人が決める（R-06）。
会場に紐付けておけば、記録画面で会場から候補を絞れて**「選ぶだけ」（F-18）が成立する。**
1つの会場に複数のルートを紐付けられる（R-07）。

**最寄り駅が同じ会場が複数あっても、ルートは共有しない。**
同じ経路でも会場ごとに1本ずつ登録する。**区間が共有されるので、運賃は重複しない。**
**ルートまで多対多にすると、1本を消しただけで複数の会場から行き方が消える。**

> **「会場ごとに到着駅が違うため、ルートは会場に固有になる」と書いていたが、これは撤回する**
> （決定18）。**最寄り駅が同じ3会場では、到着駅は違わない。**
> 1対多を保つ結論は変わらないが、**理由は上の2つである。**

### 6.2 実績データ

| エンティティ | 主な属性 |
| --- | --- |
| **案件** | 案件番号・施行日・会場コード・会場名・ご両家名・出どころ（自動取込／手動追加）・取り込み元メール |
| **交通費記録** | 案件・往路ルート・復路ルート・往復か片道か・**区間ごとの金額**（上書きされうる） |
| **タクシー乗車** | 案件・乗車日・金額 |
| **領収書** | タクシー乗車（**1対1**）・ドライブのファイルID・URL・保存日時 |
| **提出記録** | 対象月度・実行日時・書き込んだ行数 |

**関連**

```
案件 1 ──── 0..1 交通費記録
案件 1 ──── *    タクシー乗車 1 ──── 1 領収書
```

**案件が属する月度は、施行日から導出する**（決定12 / N-20）。**月度の属性は持たない。**
施行日は依頼メールから必ず取れ（F-06）、手で足した案件でも人が入れる（F-10）。
**持たせると、施行日を直したときに月度が置き去りになる。**

**取り込んだ日は月度の判定に使わない。** 月初の案件は前月末に取り込まれるため
（要求分析 2章）、取り込み日で判定すると **9月の案件が8月度のものになる。**

**案件番号は、手で足した案件では空になりうる**（F-10）。依頼メールが無いためである。
二重取り込みの防止（F-08）は案件番号を鍵にするので、**手で足した案件には効かない。**
同じ案件が後からメールで取り込まれることがあり、そのときは重複を手で消す（F-12）。

**交通費記録が金額を持つのは、ルートの運賃が後から変わっても過去の記録が動かないようにするため。**
ルートは設定データで残り続け、運賃改定で書き換わりうる。
**記録した時点の金額を実績側に持つ。**

**タクシー乗車を1件ずつ持つのは、領収書が乗車ごとに1件だから**（R-12）。
提出シートには案件ごとに合算した額を書くが（5.3）、
**領収書の URL は乗車ごとに並べる**（5.4）ため、**乗車の数と行の数は一致しない。**

### 6.3 システムデータ

| エンティティ | 役割 |
| --- | --- |
| **取り込み済みメール** | メールの識別子・処理結果（案件にした／依頼無しで除外／解析に失敗）・処理日時 |
| **同期状態** | 最後に取り込んだ日時・**最後に読んだ提出シートの月度** |
| **要確認事項** | 種別・内容・発生日時・確認済みか |
| **認可情報** | Google API のトークン。**バックエンドだけが持つ**（2.1） |

**取り込み済みメールは、二重取り込みの防止（F-08）と、解析失敗の記録（F-07）を兼ねる。**
案件を手で削除した場合（F-12）、そのメールは「処理済み」のまま残す。
**残さないと、次に開いたときに同じ案件がまた入ってくる。**

**同期状態の「最後に読んだ月度」が、月度切替の検知に使われる**（F-32）。
今読んだ値と違っていれば、シートが消去されて次の月度に入ったということ（要求分析 5.6）。

### 6.4 保持期間と削除

| 何が | いつ消えるか |
| --- | --- |
| 実績データ（案件・交通費記録・タクシー乗車・領収書のレコード） | **月度の切り替わりを検知したとき。ただし切り替わった先より前で、かつ提出が済んだ月度のものだけ**（F-32） |
| 案件に紐づく実績 | **その案件を削除したとき**（F-12） |
| 設定データ | **消えない**（N-06） |
| 取り込み済みメール | 実績データと一緒には消さない。**再取り込みを防ぐため残す** |
| 要確認事項 | 確認済みにしたら消してよい |

**「実績データは月度の切り替わりで消える」を無条件に読まない。**
切替の時点でアプリの中には**翌月第1週の案件も入っている**（9.2）。
どの月度のものかは**施行日**で決まり（決定12）、**切替先以降の月度は消さない**（F-32）。

**ドライブに保存した領収書ファイルは、アプリからは消さない。**
提出後の正本は提出シートとドライブにある（N-05）。
**アプリが消してよいのは、自分が持っているレコードだけである。**

## 7. 外部連携仕様

### 7.1 認可とスコープ

必要な権限は次の4つ。**いずれもバックエンドが保持する**（2.1）。

| 用途 | 権限 |
| --- | --- |
| 依頼メールを読む | **読み取りのみ。** メールの変更・削除はしない |
| **提出アラートを送る** | **メールの送信**（F-35 / 決定17） |
| 領収書の保存と共有 | ドライブへの書き込み |
| 提出シートの読み書き | スプレッドシートの読み書き |

**送信の権限は、決定17 で新しく増えたものである。**
それまでは「メールの変更・送信はしない」と書いていた。**読むだけの側から、送る側になった。**
広げたぶんの歯止めを、要件として置く。

| 歯止め | |
| --- | --- |
| **宛先は本人のアドレス固定**（NF-13 / N-23） | 実行時に宛先を組み立てない |
| **送るのは提出アラートだけ**（F-35） | 他の用途では送らない |
| **依頼メールには触れない** | 返信も転送もしない。読むほうは変わらず読み取りのみ |

ログイン（F-01）にはこれとは別に、**本人であることを確かめる**ための情報だけを使う。

**認可が失われたら検知して知らせる**（F-02）。失われ方は2つあり、扱いが違う。

| 失われ方 | 兆候 | すること |
| --- | --- | --- |
| **アプリの認可が切れた** | API が認可エラーを返す | 再認可へ導く |
| **提出シートの共有が締められた**（N-13） | シートだけが読めなくなる | **知らせる。アプリ側では復旧できない** |

### 7.2 Gmail — 依頼メールの取り込み

**集め方**

| # | すること | 根拠 |
| --- | --- | --- |
| 1 | **差出人アドレスで絞り込む。** ラベルは条件にしない | N-15 |
| 2 | 前回の取り込み以降に届いたものだけを見る | — |
| 3 | **件名で種別を判別する。** 依頼無しのメールは、処理済みとして記録し取り込まない | R-19 |
| 4 | 既に取り込んだメールは飛ばす | F-08 |

**宛先（`To`）は判別に使わない**（N-17）。依頼無しメールでは自分が `To` に居ない。

**読み方**

本文は `text/plain` と `text/html` の**両方を使う**。片方だけでは足りない（要求分析 6.2）。

| パート | 使いどころ |
| --- | --- |
| `text/plain` | 各項目の値。リンクの URL が本文に並ぶ |
| `text/html` | 表のセル境界。**スタッフの割当は HTML 側でないと切り分けられない** |

**取り出す項目と裏の取り方**

提出に要るのは4項目（施行日・会場コード・ご両家名・案件番号）。会場名も併せて取る。

| 項目 | 取り方 | 裏の取り方 |
| --- | --- | --- |
| 施行日 | `施行日` の見出しから | 見出しがある |
| 案件番号 | `案件番号` の見出しから | 見出しがある |
| 会場名 | 先頭ブロックの2行目 | **下記** |
| 会場コード | 先頭ブロックの3行目 | **下記** |
| ご両家名 | 先頭ブロックの4行目 | **下記** |

**先頭の4行には見出しが無く、位置で読むしかない**（要求分析 6.3）。そこで、

1. **1行目の日付が「施行日」の日付と一致すること**
2. **4行目が `〇〇様 △△様` の形であること**

の**両方を確かめてから**、2行目を会場名・3行目を会場コードとして採る。
**どちらかが崩れたら、値を採らずに「取り込めなかった」として記録する**（F-07 / N-16）。

**書式が変われば裏取りが失敗する。それでよい。**
黙って別の値を拾って提出してしまうより、取り込めていないと分かるほうが良い。

**取り込んだ案件に、C列の目的は常に `婚礼案件` を割り当てる**（要求分析 5.2）。

**リンクは叩かない。** 依頼メール内のリンクは委託元の配信サービスの計測用 URL であり、
**叩けば計測される**（要求分析 6.3）。案件承諾は今回扱わない（11章）。

### 7.5 Gmail — 提出アラートの送信

**読むのと同じ Gmail を、送信にも使う**（決定17）。別のメール送信サービスを持たない。

| # | すること | 根拠 |
| --- | --- | --- |
| 1 | **1日1回、定期実行で起動する** | NF-04 / 2.1 (3) |
| 2 | **その日が1日でも3日でもなければ、何もせずに終わる** | F-35 |
| 3 | 対象月度を読む（自分のシートの `A1`） | F-31 |
| 4 | **その月度の提出記録があれば、何もせずに終わる** | F-36 |
| 5 | **本人のアドレスあてに1通送る** | F-35 / NF-13 |

**手順3で `A1` を読めなかったときは、対象月度を書かずに送る。**
提出シートが読めないこと自体が、知らせるに値する（N-13 / F-02）。
**読めないから黙る、という振る舞いにはしない。**

**送信に失敗したら要確認事項に残す**（F-33）。次にアプリを開いたときに分かる。
**ただし、アラートが届かなかったこと自体は検知しない**（10章）。

**採らなかった案**

- **AWS SES など別のメール送信経路** — Gmail のスコープを読み取りのままに保てるが、
  **送信元の検証など AWS 側の設定が増える。** しかも目的②（無料構成への移行・
  [`architecture.md`](design/architecture.md) 1章）で作り直しになる。
  **Gmail なら、移行先が変わっても同じまま動く**
- **アプリを開いたときに画面で警告するだけ** — 決定1 をそのまま守れるが、
  **開かない人に届かない。** アラートが要る場面でだけ働かない
- **カレンダーの繰り返し予定など、アプリの外で持つ** — 構成は一切変わらないが、
  **提出済みでも毎月届き**、記録の過不足も分からない。**届いたことが合図にならない**（F-36）

### 8.1 いちばん短くすべき操作

**帰り道の記録は3手で終わる**（R-10 / N-01）。

```
ホーム            案件の詳細         交通費の記録
  │                  │                  │
  ├─ 今日の案件 ──→  ├─ 記録する ──→   ├─ ルートを選ぶ
                                        └─ 保存
```

- ルートが1つしか紐づいていない会場なら、**選択済みの状態で開く**
- 金額は選んだ時点で入っている。**直す必要が無ければ触らない**（F-20）
- タクシーに乗った日は、ここに **金額と領収書のアップロードが2手**加わる

**この経路にキーボード入力を要求しない。** 屋外・移動中に文字を打たせる作りにすると、
「その場で終える」（シーン②）が成立しない。

### 8.2 ホームが見せるもの

**ホームは「提出までに何が足りていないか」が分かる場所である。**

| 見せるもの | なぜ |
| --- | --- |
| **提出待ちの月度と、これから稼働する案件。月度ごとに区切って見せる** | **月末から月初にかけて2つの月が並走する**（9.2）。混ぜて並べると、どれが提出対象なのか分からない |
| 案件ごとの**記録の済み／未** | 提出前に「揃っているか」を確かめる土台（R-02） |
| 要確認事項の件数 | 気づかないまま提出しないため |
| **最後に取り込んだ日時** | 取り込みが静かに止まっていることに気づくため（10章） |
| 提出済みかどうかと、その日時 | F-30 |

### 9.2 月度の並走

**2つの月が同時に存在する期間は、月初だけではない。月末から始まっている。**

依頼は月曜に届く（要求分析 2章）。
したがって **月末の最終月曜の時点で、もう翌月第1週の案件が入ってくる。**
**2026-08-31（月）に 9/5・9/6 ぶんが届いた実測が、これにあたる**（要求分析 6章）。

| 時期 | アプリの中にあるもの |
| --- | --- |
| 当月中（最終月曜より前） | 当月分の記録 |
| **月末の最終月曜〜月末** | **当月分（記録中）と、翌月第1週分（施行前）の両方** |
| **翌月1〜3日** | **前月分（提出待ち）と、当月分（記録中）の両方** |
| 翌月4〜7日 | 月度が切り替わり、**提出済みの前月分が消える。当月分は残る**（F-32） |

したがって **アプリは常に2か月分を保持できる**必要がある。
「前月分だけを扱う」（N-05）は保持期間の話であって、
**同時に1か月分しか持てないという意味ではない。**

**2か月で足りる根拠は、配信が覆う範囲を計算できることにある**（要求分析 2章 / N-21）。
配信は月曜 M で、覆う最も遠い日は **M+7**（土日に連なる月曜の祝日・決定16）。
M が前月に属する最後の月曜なら **M は前月の末日から6日以内**にあるので、
**M+7 は翌月1日から7日のあいだ**にしかならない。
先の月度として持つのは **翌月第1週分だけ**で、それより先の案件は入ってこない。
**3か月分が同時に並ぶことはない。**

> **決定16 の前は「前の週には届かない」を根拠にしていた。**
> 祝日でそれが崩れたので、根拠を **M+7 の計算**へ置き換えた。**結論は変わっていない。**

**月初に稼働日がある月では、1回の取り込みで2つの月度の案件ができる。**
2026年11月1日は日曜で、その週の月曜は 10/26。**10/31（土）と 11/1（日）の依頼が同じ日に届く。**
月曜が祝日なら、その月曜ぶんも同じ回に入る。
取り込み処理は、**1回の実行で複数の月度にまたがる案件を作れなければならない。**

## 10. 異常系と復旧

**この章の関心は「静かに壊れないこと」である。**
例外が出て止まるより、**間違った値が黙って提出されるほうが害が大きい。**

| 起きること | どう気づくか | どう直すか |
| --- | --- | --- |
| **依頼メールの書式が変わった** | 裏取りが失敗し、要確認事項に出る（F-07） | 案件を手で足す（F-10）。解析の実装を直す |
| **依頼メールの差出人が変わった** | **案件が入ってこない。** ホームの「最後に取り込んだ日時」が古いままになる | 差出人の設定を変える（環境依存値） |
| 会場コードがマスタに無い | 提出前の照合で警告が出る（F-27） | **そのまま書く**（N-14）。会場をアプリに追加しておく |
| **提出シートの共有が締められた** | 読み書きが認可エラーになる（F-02 / N-13） | **アプリ側では直せない。** 委託元へ確認する |
| **提出シートの様式が変わった** | ヘッダーの並びが想定と違い、提出が中止される（5.5） | 実装を直す。それまでは手で入力する |
| 行が足りない | 提出時に自動で挿入され、要確認事項に残る（5.2 手順5） | 対応不要。**シートの構造を変えたことを知っておく** |
| ドライブへの保存に失敗した | その場で失敗が出る（F-26） | やり直す。**記録は残らないので中途半端にならない** |
| 同じ案件が二重に入った | 一覧で分かる | 手で削除する（F-12） |
| **未提出のまま月度が切り替わった**（切り替わった先より前の月度に限る） | 実績は消えず、要確認事項に出る（F-32） | **アプリでは扱わない**（決定14）。提出シートの運用に従い、**手で入力する**（要求分析 5.4） |
| 提出後に差し戻された | 委託元から連絡が来る | **アプリ側を直して、もう一度提出する**（F-29） |
| **提出アラートを送れなかった** | 要確認事項に出る（7.5） | 次に開いたときに分かる。**送れなかったこと自体は提出を妨げない** |

**アラートが届かなかったこと自体は、検知しない。**
送信に失敗すれば要確認事項に残るが、**それを見るにはアプリを開かなければならない。**
受信側で迷惑メールに入るような届かなさは、**アプリからは分からない。**
**F-35 は提出を保証する仕組みではなく、気づく手立てを1つ増やすものである**（R-22）。

**「最後に取り込んだ日時」をホームに出すのは、2行目のためである。**
差出人が変わると、**エラーは何も出ない。** ただ案件が入ってこなくなるだけで、
**気づけるのは「いつまでも新しい案件が増えない」ことだけ**である。
土日祝の稼働で月6〜10件という頻度では、しばらく気づけない恐れがある。

**月度の切り替わりで翌月の案件が消えるのは、この表のどの行にも書けない壊れ方である。**
気づく手立てが無く、直す手立ても無い。取り込み済みメールが残るので再取り込みもされず
（6.3）、**本人がその案件を覚えていなければ、消えたことにすら気づけない。**
しかも切替期間（翌月4〜7日）は、**まさにその案件の稼働日と重なる。**

だから F-32 は「切り替わった先より前で、かつ提出が済んだ月度」だけを消す（決定12）。
**異常系として扱うのではなく、起こらない作りにする。**

## 11. 対象外

要求分析9章のものは、そのまま対象外とする。加えて、要件定義の検討で対象外にしたもの。

| やらないこと | 理由 |
| --- | --- |
| **オフラインでの入力** | 決定7。入力は数分で終わり、電波のある場所で済ませられる |
| **祝日カレンダーを持つこと** | 決定15 / N-22。**アプリが祝日を判定する箇所が1つも無い。** 施行日は依頼メールから来る値である |
| **提出アラートを送ったあとの追跡** | F-35 は知らせるところまで。**読んだか・押したかを追わない。** 見たうえで忘れたら手で書く（決定14 / R-22） |
| 提出済みデータの閲覧・集計 | 提出後のデータは残さない（N-05）。提出シート自体も毎月消去される |
| 領収書のドライブからの削除 | 提出後の正本はドライブにある（N-05）。**アプリが消してよいものではない** |
| 提出シートの様式変更への自動追従 | 変わったら**止まって知らせる**（NF-10）。自動で合わせにいくと、間違った欄へ書く危険がある |
| **月度切替後に、前月分を翌月度シートへ申請すること** | 決定14。年に何度あるかの例外のために、**対象月度と施行日がずれる経路**を作らない。5.5 の中止条件と 5.3 の絞り込みを素直に保つほうが安全で、その分は手で入力すれば済む |
| 複数の委託元・複数ユーザー | 要求分析9章のとおり |

> **「提出期限（翌月3日正午）のリマインド」は、この表に載っていた。**
> 外していた理由は2つで、**要求に無いこと**と、**通知の仕組みが決定1 と噛み合わないこと**だった。
> 2026-09-04 に要求として出たので前者は消え、後者は **定期実行を1本だけ持つ**ことで折り合わせた
> （決定17 / 2.1 (3)）。要件は **F-35 / F-36** にある。

## 13. 未確定事項

**設計・実装に入る前に決めればよいもの。要件としては固まっている。**

| 何が | 何が決まっていないか | いつ決めるか |
| --- | --- | --- |
| **ドライブの権限の粒度** | 既存の保管先フォルダへ保存するのに、アプリが作ったファイルだけを扱える権限で足りるか。足りなければ広い権限が要る | 実装時に実機で確認 |
| **定期実行が落ちたことに気づく手立て** | 置き場は [`architecture.md`](design/architecture.md) 3.8 で決めた（`docker compose` 内の専用コンテナ）。**コンテナが起動しなくなったことをどう知るか**が残っている（7.5） | 設計（`error-handling.md`） |
| **締切が祝日にあたる年の扱い** | 締切は翌月3日正午だが、**5/3・11/3 は祝日、1/3 は年始**にあたる。委託元が期限を動かすかどうかを確かめていない。**動かないなら、アプリ側ですることは何も無い** | 委託元へ確認 |
| **月曜祝日の依頼配信** | 決定16 は本人談で、**実測できていない**（要求分析 10章）。次の月曜祝日に `tools/gmail-probe/` で確かめる | 次の月曜祝日 |

**設計で閉じたものは、この表から落としている。**
**領収書のファイル名**は [`database.md`](design/database.md) 5.2 で `<YYYYMMDD>_<会場コード>_<連番>` と決めた。
**設定データの控え**は [`architecture.md`](design/architecture.md) 8章で、
設定画面からの JSON の書き出しと読み込みと決めた。

**「一括更新の原子性」は、確かめる必要が無くなったので落とした。**
[`integration.md`](design/integration.md) 8.2 が、**本文行を「書く行＋空行」の矩形として
1回の書き込みで送る**形にした。**クリアという操作が消えたので、
「クリアが通って書き込みが失敗する」という状態そのものが作れない。**
5.2 手順8 の「1回の一括更新にまとめる」は、**これで満たされている。**

**残りの大半は、要件が決まったうえでなお残る実現方法の選択である。** 要求が未確定なわけではない。

**ただし下の2行は性質が違う。**「締切が祝日にあたる年の扱い」と「月曜祝日の依頼配信」は、
**実現方法ではなく事実の確認**である（要求分析 10章）。
どちらも本人談があり、**規則のほうを広めに書いてあるので、設計を止める理由にはならない。**
